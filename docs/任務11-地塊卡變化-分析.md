## 2. M-series 後端與 WorldMap 的差異盤點

| 維度 | WorldMap（runtime 現用） | GameState（M-series 後端） | 衝突點 |
|---|---|---|---|
| 座標系 | 9×9 固定，玩家起點 (4,4) | 無界 `Dictionary<(int X, int Y), PlacedTile>`，起點 (0,0) | 🔴 全 UI / 投影 / 攝影機都依賴 9×9 bounds |
| 回合命名 | `Turn 1..30`、ApMax=3 | `CurrentBigRound 1..MaxBigRounds`（從 module）、ActionPoints=3 | 🟡 命名不同；TopBar / TURN LOG 顯示要改 |
| 玩家數 | 單一玩家 (`PlayerPos`) | `Players: List<PlayerState>`、`CurrentPlayer` | 🟢 **鎖定單人**：`state.Players[0]` 永遠是 currentPlayer（任務 11 不開多人；後續 Phase 3+ 才考慮） |
| 地形模型 | `MapTerrain` enum（6 種） + PNG 表 | `Tile.Terrain` string（"town"/"wilderness"/...） + `TileId` 路由到 module.Tiles | 🔴 渲染層需要 `TileVisualProfile`：以 **TileId** 為 key 對應 (MapTerrain enum, minimapColor, sceneTheme)，不能只用 terrain string（一對多衝突，例：wilderness 可能涵蓋 forest/swamp/desert） |
| 地塊資料 | `TileData(Row, Col, Terrain, IsPlaced, IsExplored)` immutable | `PlacedTile { TileId, Level, ProgressGainedThisBigRound, ... }` mutable | 🟡 IsExplored ↔ Level（Unknown/Unfamiliar/Familiar/...） 需對應 |
| 卡牌系統 | `WorldMap._hand`、`_actionDeck`、`_companions`、`_equipped` | `PlayerState.Hand/Deck/Discard/Equipment` + `CompanionState` | 🔴 Task 7 卡牌系統雙寫；要選定權威來源 |
| 互動模式 | `InteractionMode { Idle, MapExpand, Move }` | `TurnPhase { Draw, MapExpand, Action, EventCheck, TurnEnd }` | 🟡 Mode 概念不同層級 |
| 事件 | `WorldMap.TileChanged/TilePlaced/HpChanged/...` 一堆 .NET event | GameState **沒有** event；mutation 後由 service 主動 emit | 🔴 UI 訂閱模式要全改 |
| Module 載入 | 沒有 — 起手地塊 hard-code in WorldMap.cs | `ModuleLoader.Load(modulePath)` → `Module` → `GameState.CreateNew(module, characters, companions, seed)` | 🟢 ModuleLoader 已成熟 |

🔴 = 高衝突（重大改寫） / 🟡 = 中衝突（介面調整） / 🟢 = 低衝突（直接接）

## 3. 目標架構（Migration 後）

```
MainBootstrap._Ready
├─ ModuleLoader.Load("modules/builtin/abandoned-mansion") → Module
├─ GameState.CreateNew(module, [hero], [companion], seed) → GameState
├─ TurnLoop(state, module, services)  ← 取代 WorldMap 的回合驅動
├─ EventResolver / EventOrbitResolver / EffectHandler / EffectsService
└─ MainMap (= WorldMap façade) 訂閱 GameState 變化 emit Godot Signal

WorldMap 角色重定位：
  舊：authoritative 9×9 game state
  新：thin façade / projection — 包 GameState 提供 9×9 bounded view + MapTerrain 翻譯 + 既有 .NET event
```

**關鍵設計**：保留 `WorldMap` API surface（給已寫好的 MainMapRenderer / MinimapRenderer / LeftPanel / HandDock 用），內部改成讀 `GameState`。Mutation 全走 GameState，WorldMap 在 service callback 裡 emit 對應 .NET event。

### Stage 2 — WorldMap 改 façade（讀路徑 + 單一權威 + 投影 cache）

> **v3 修訂**：原版「雙寫」會留下兩個 source of truth，漏 mirror 會產生 GameState/WorldMap 不一致的隱性 bug。升級為「**單一權威 + 投影 cache**」：GameState 永遠是唯一權威，WorldMap 只做兩種事 — (a) 讀 GameState（原始型別） + (b) 維護衍生 cache（如 `_hand: List<ActionCard>` 是從 `state.Hand: List<string>` × `module.ActionCards` 投影出來的）。Mutation 進 WorldMap entry point 後**只寫 GameState**，再 invalidate cache 並重建。
>
> 這個改變使「漏 mirror」不可能發生 — 因為沒有獨立 mirror 寫入路徑可以漏。

| 軸 | 內容 |
|---|---|
| **方向** | GameState 為唯一 source of truth；WorldMap 退化為「讀 + 投影 cache」 |
| **方式** | 1) **Getter 切換**：`WorldMap.PlayerPos => (state.Players[0].Position.Y, state.Players[0].Position.X)`（單人鎖定 Players[0]）、`GetTile(r, c) => TileVisualProfile.Resolve(state.TileMap[(c, r)], module)` 翻譯成 `TileData`、`Hp/HpMax/Ap/Turn` 全部改 computed property 讀 GameState（**無內部欄位**）；<br>2) **建 `TileVisualProfile`（精細路線）**：tile.json 加 `visualProfile: { terrain: "Forest", minimapColor?: "#3a6830", sceneTheme?: "forest-day" }` 選用欄位；ModuleLoader 解析；逐個替 14 個 tile 補 visualProfile；fallback 表保留作為缺欄位的安全網（wilderness→Forest / town→Building / road→Path / field→Grass / water→Water / mountain→Mountain）；<br>3) **投影 cache**（針對需要型別轉換或聚合的衍生資料）：例 `_hand: List<ActionCard>` 由 `state.Hand: List<string>` 投影；Hand 的 mutation API 走 `state.Hand.Add(cardId)` → 觸發 `RebuildHandCache()` → emit `HandChanged`。**沒有獨立的 _hand 寫入路徑**；<br>4) **單寫 mutation**：`TryPlaceHeldTile` / `TryConsumeAp` / `TryPlayCard` 等 entry point 內**只寫 state**（不寫 cache），最後呼叫 `InvalidateCachesAndEmit(...)` 重建 cache + 按序 emit event；<br>5) **既有 .NET event 仍由 WorldMap emit**（Stage 3 加排序層；本 stage 順序仍與 Phase 1+2 等價）；<br>6) `Companions` 從 state.Companions + module.NpcCompanions 組合的 cache |
| **目標** | UI 資料源切換到 GameState；不可能出現雙寫不一致 |
| **成果** | UI 不變、行為不變；本 stage 結束點 push 一次仍可玩；無「漏 mirror」風險 |
| **風險** | 🟡 cache invalidation 漏 — 某 mutation 改了 state 但忘了重建 cache → emit 用舊 cache；緩解：抽 `InvalidateCachesAndEmit(scope)` helper 集中重建邏輯，scope 限定對應該 mutation 影響的 cache（如 hand mutation 只重建 hand cache）；<br>🟡 IsExplored 對應 `placed.Level >= Familiar`；<br>🟡 14 個 tile visualProfile 手動填寫工：~15 分鐘 JSON 編輯；<br>🟢 fallback 表作為安全網，未來新模組作者忘記填 visualProfile 也不會炸 |
| **工時** | 5-6 h（含 14 tile visualProfile JSON 編輯 ~15 min） |

### Stage 3 — WorldMap 純 façade（寫路徑 + 事件排序層 + 嵌套支援）

> **v3 修訂三點**：
> 1. **嵌套事件**：原版只說「mutation 結束 flush」，但 `PlayCard → EventResolver → Effect A → trigger another event → Effect C` 這類嵌套會在 inner mutation 提前 flush 半完成事件。改用 `eventDepth` 計數器，**只在最外層 flush**。
> 2. **事件順序硬編碼脆弱**：原版列死順序（TileChanged → PlayerMoved → ...），未來加新事件（BuffApplied / StatusEffectChanged）要改硬編碼。改成 `enum EventPriority`（每個事件型別綁數值），buffer flush 時依 priority 排序。
> 3. **WorldMap state 一刀刪太激進**：原版直接砍 `_hand` 等內部 state，但 UI 或測試可能還偷用。改成 `[Obsolete("Use GameState")]` 標記、留警告 log、跑一輪確認沒人用後再刪（Stage 3.5 清理階段）。

| 軸 | 內容 |
|---|---|
| **方向** | mutation 全派去 GameState；事件排序層處理嵌套 + priority；WorldMap 內部 state 漸進式廢除 |
| **方式** | 1) **Mutation 改派**：`TryPlaceHeldTile` → `MapService.ExpandTile(state, ...)`、`TryConsumeAp` / 移動 → TurnLoop / Action 路徑、`TryPlayCard` → 走 GameState.Hand 操作；<br>2) **WorldMap state 漸進廢除（不一次刪）**：Stage 2 留下的 cache（如 `_hand: List<ActionCard>` 投影）保留；任何**仍在用獨立寫入路徑**的舊欄位先標 `[Obsolete("Use GameState; will be removed in Stage 3.5")]` + runtime 警告 log，跑全測 + L2 操作確認無剩餘呼叫者後 Stage 3.5 清理；<br>3) **Event Adapter（含嵌套支援）**：建 `WorldMapEventBuffer` — service 層 mutation 完成後不直接 emit，而是 buffer + `eventDepth` 計數器：<br>&nbsp;&nbsp;&nbsp;&nbsp;`BeginEvent() { _eventDepth++; }`<br>&nbsp;&nbsp;&nbsp;&nbsp;`EndEvent() { if (--_eventDepth == 0) Flush(); }`<br>&nbsp;&nbsp;&nbsp;&nbsp;mutation entry point / EventResolver 入口呼叫 `BeginEvent`，離開呼叫 `EndEvent`；<br>4) **EventPriority enum（取代硬編碼順序）**：`enum EventPriority { TileChanged=10, TilePlaced=15, PlayerMoved=20, HpChanged=30, ApChanged=35, HandChanged=40, ModeChanged=50, CompanionChanged=60, TileTransformed=70 }`（數值間距 5/10 為未來插入留空間）；Flush 時 `buffer.OrderBy(e => (int)e.Priority).Distinct()` 後依序 emit；<br>5) **ORBIT 結算接上**：當前 [MainBootstrap.cs:321](scripts/MainBootstrap.cs#L321) TODO 點改呼叫 `EventResolver.ResolveEvent(state, card)` → 套 outcome.Effects 走 EffectHandler；entry 點 `BeginEvent`、結束 `EndEvent`，effects 套用過程的所有事件累積 buffer，最外層 flush 一次重排 emit |
| **目標** | 操作真正改 GameState；UI 訂閱順序穩定（priority enum）；嵌套事件不出半完成幀；WorldMap state 安全漸進廢除 |
| **成果** | 端到端「行為一致性」恢復；EventResolver / EffectHandler 自動跑；UI 無偶發順序 bug；無 deprecated state 殘留（Stage 3.5 後） |
| **風險** | 🔴 既有 WorldMap mutation 行為要與 TurnLoop 對齊（特別 `_actionDeck.Draw()` vs `TurnLoop.DoDraw`）；<br>🔴 Phase 1+2 P0 完整探索流程（任務 6）不能爆 — Stage 3 結束立即跑 L3-01 happy path 把關，不過就 rollback；<br>🔴 既有 355 個 xUnit 中對 WorldMap mutation 的測試需重新指派為 façade 測試或 GameState 測試；<br>🟡 嵌套深度警告：若 `_eventDepth > 5` 印錯誤 log（避免無限遞迴或 stack 失衡）；<br>🟡 EventBus（Task 9）信號要對齊 EventResolver — 統一所有 ORBIT 事件走 EventResolver，EventBus 只做 UI signal bridge |
| **工時** | 7-10 h（+1h：嵌套支援 + priority enum + obsolete 漸進） |

### Stage 5 — Tile transform rules schema + EventCheck 階段觸發

> **修訂說明**：原版「事件 trigger 後遍歷 9×9 tile 呼叫 TryTransformTile」是 O(81 × R) per event。9×9 還能擋，但設計時就該避免 — 改用 **event-indexed transform registry**：模組載入時建 `Dictionary<EventId, List<TileTransformRule>>`，事件觸發只查該 event 訂閱清單，O(R)。未來 Task 14 地圖擴大或 transformation 多時直接受惠。

| 軸 | 內容 |
|---|---|
| **方向** | `transformTile` 從 event outcome 變到 tile 自身規則（§1.5 `TileTransformRule`），並建 event-indexed registry 避免 O(n²) |
| **方式** | 1) `tiles.json` 加 `transformations: [{ triggerEventId, transformsTo (tileId), condition? (JsonLogic) }]` 選用欄位；<br>2) `Tile` model 加 `Transformations: List<TileTransformRule>`；<br>3) **建 `TileTransformRegistry`**：模組載入時掃所有 tiles 的 transformations，建 `Dictionary<EventId, List<(TileId SourceTileId, TileTransformRule Rule)>>`；<br>4) `MapService.TryTransformTile(state, module, row, col, triggeredEventId, jsonLogicCtx)` — 從 registry 查 triggeredEventId 對應的規則清單，掃 `state.TileMap` 找 TileId 符合 SourceTileId 的格、評估 condition，符合則 `EffectHandler.ApplyTransformTile` 套 `TransformTileEffect{NewTileId=rule.TransformsTo}`；<br>5) EventResolver 在事件 trigger 後**僅查 registry 一次**呼叫 `TryTransformTile`（不遍歷整張地圖）；<br>6) 起始模組 `tiles.json` 加 1-2 個 demo（如 `forest-path` 在 `fire-spreads` 事件 → `forest-burnt`，需新增 `forest-burnt` tile 條目） |
| **目標** | 規格 §1.5 的 tile-side transformation 完整；轉變查找 O(R) 不 O(n×R) |
| **成果** | L1 `MapService_TryTransformTile_PreservesPositionAndExplored / ConditionFalse_NoChange` 通過 |
| **風險** | 🟡 module schema 升級（需要 JSON schema 的 transformations 欄位；ModuleLoader 解析）；<br>🟡 既有 `forest-path` tile 沒有 `forest-burnt` 對應紋理 — 美術未到位先用 `forest-path` 自身或備用色塊；<br>🟢 registry 是不可變字典，模組載入後 read-only — thread-safe 直接 ok |
| **工時** | 3-4 h |
| **未來優化（v3 補註，現不做）** | 若未來地圖變大或 transformation 數量增加，可進一步把 registry 升級為 `Dictionary<EventId, Dictionary<TileId, List<TileTransformRule>>>` + `Dictionary<TileId, List<Position>>` 反向索引（TileId → 已放置的 Position 清單），事件觸發定位變 O(R + k)（k = 該 TileId 數量）。本 stage 架構已接近，加反向索引只需 ~1h。 |

## 9. 修訂紀錄

### v2 — 技術審查修訂

針對原版 5 個技術盲點修正：

| 盲點 | 原版做法 | v2 修訂 | 影響 |
|---|---|---|---|
| **Stage 2 半同步狀態** | 純 getter 切換 → mutation 仍寫 WorldMap → getter 讀 GameState → UI 顯示舊值 | 雙寫過渡：mutation 同時寫兩邊 | Stage 2 工時 +1h；後又被 v3 取代為「單寫 + cache」 |
| **Stage 3 事件順序不一致** | service 散發事件 → WorldMap 直接轉發 → 順序可能反轉 → 偶發 UI bug | 加 `WorldMapEventBuffer` 排序層：buffer + reorder by canonical order | Stage 3 工時 +1-2h；後又被 v3 增強（嵌套支援 + priority enum） |
| **MapTerrain 翻譯一對多** | terrain string → MapTerrain enum（wilderness→Forest），但 wilderness 涵蓋 forest/swamp/desert 視覺撞色 | 改用 `TileVisualProfile`：keying by **TileId**，fallback 才走 terrain mapping | 設計修正；schema 加 visualProfile 選用欄位 |
| **Stage 5 O(n×R) 遍歷** | 事件觸發遍歷 9×9 tile 對每格檢查 transformations | 建 `TileTransformRegistry`：`Dictionary<EventId, List<TileTransformRule>>`，O(R) 查找 | Stage 5 工時持平甚至略省 |
| **Stage 7 EffectsService 偷做** | 直接讀 `apCostBonus` / `rollBonus` 欄位 → Task 13 完整 EffectsService 時被重寫 | 抽 `ITileEffect` 介面，兩個實作 | Stage 7 工時 +0.5h；省 Task 13 重寫成本 |

### v3 — 第二輪技術審查修訂

針對 v2 後仍存在的 5 個「實作期會踩雷」的點修正：

| 盲點 | v2 做法 | v3 修訂 | 影響 |
|---|---|---|---|
| **Stage 2 雙寫一致性風險** | mutation 同時寫 WorldMap + GameState（兩個 source of truth，漏 mirror = 隱性 bug） | 升級為「**單寫 + cache**」：GameState 唯一權威，WorldMap 只做讀 + 投影 cache；mutation 只寫 state，呼叫 `InvalidateCachesAndEmit(scope)` 重建 cache + emit。**不存在 mirror 寫入路徑可漏** | Stage 2 風險從 🔴 降到 🟢；工時不變 |
| **Stage 3 嵌套事件提前 flush** | 「mutation 結束 flush」沒處理 `Effect A → trigger event → Effect C` 嵌套 | 加 `eventDepth` 計數器：`BeginEvent { _eventDepth++ }` / `EndEvent { if (--_eventDepth==0) Flush() }`；只在最外層 flush | Stage 3 +0.5h；防半完成幀 |
| **Stage 3 順序硬編碼脆弱** | canonical order 列死 `TileChanged → PlayerMoved → ...`，加新事件要改硬編碼 | `enum EventPriority { TileChanged=10, PlayerMoved=20, ... }` 數值間距 5/10 為未來預留；flush 用 `OrderBy(priority)` | Stage 3 +0.5h；可擴充 |
| **Stage 3 一刀刪 state 太激進** | 直接砍 `_hand` 等 → 漏處 UI 偷用會 crash | 三步走：`[Obsolete]` 標記 + warning log → 跑全測 + L2 → Stage 3.5 清理階段刪 | Stage 3 +0h（清理延後）；風險從 🔴 降到 🟡 |
| **Stage 5 O(n) 掃 TileMap** | `Dictionary<EventId, List<(TileId, Rule)>>` 然後掃 TileMap 找 matching | （v3 補註，**現不做**）未來可加 `Dictionary<TileId, List<Position>>` 反向索引；架構已接近，未來只需 ~1h | 不影響本任務工時；註記為將來優化點 |

**v3 淨工時影響**：v2 26-35 h → v3 27-37 h（+1-2 h，反映嵌套支援 + priority enum + obsolete 漸進）。**任務 11 範圍（Stage 0-6）= 23-32 h**。

**為何 v3 仍值得做**：
1. v2 的「雙寫」會留下「漏 mirror = 隱性 UI 閃錯一幀」的隨機 bug — v3 用「單寫 + cache」結構性消除
2. v2 的「順序硬編碼」會在 Task 12（訊息氣泡）/ 13（戰鬥）加新事件時被反覆修改 — v3 priority enum 讓加事件變局部修改
3. v2 的「一刀刪 state」會把 façade 切換的風險集中在一個 commit — v3 漸進廢除把風險攤平到 Stage 3 + Stage 3.5 兩個 commit
