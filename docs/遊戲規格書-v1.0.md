## 0. 文件說明

### 0.1 文件目的與需求書的關係

| 文件 | 內容定位 | 維護重點 |
|------|---------|---------|
| 專案設計需求書 v1.7 | **What & Why**：規則、玩法、體驗、資料結構 | 由設計與 PM 維護；本文件不重複描述 |
| **遊戲規格書 v1.0（本文件）** | **How & Verify**：實作方式、Service 命名、驗證項 | 由開發團隊維護；每個 Sprint 完成後勾選 checklist |

凡涉及「規則本身應該如何」的爭議 → 以**需求書**為準；凡涉及「程式應該怎麼寫」的選擇 → 以**本規格書**為起點，並可在 PR 中提案修訂。

### 0.2 模組編號規則

本規格書的模組編號**直接對應需求書章節**：

- §1.1 ~ §1.12 → 對應需求書 §3.1 ~ §3.12（核心機制）
- §2.1 ~ §2.4 → 對應需求書 §5.1 ~ §5.4（子系統呈現）

每個模組的標題會在括號內標註對應需求書章節，方便雙向查閱。

### 0.3 三層驗證的定義

每個模組的「驗證實作成果」採三層並列，缺一不可：

| 層級 | 名稱 | 工具 / 場景 | 涵蓋對象 | 範例 |
|------|------|-----------|---------|------|
| **L1** | xUnit 自動化 | `xUnit` + `FluentAssertions`（headless，CI 可跑） | 純 `core/` C# 邏輯 | `TurnLoop_FirstTurnSkipsMapExpand_DrawIsFirst()` |
| **L2** | Godot 手動操作 | Godot Editor 內以玩家視角 click / drag | UI、動畫、Signal、Node 行為 | 「進入 Action 階段，點擊角色所在格 → 確認觸發器彈出於正確位置」 |
| **L3** | 跨模組整合 | Godot Editor + Game Lifecycle 端到端 | 多 Service 串聯、回合循環、副作用傳播 | 「完成一整回合（5 階段）、ORBIT 連鎖、戰鬥觸發、自動存檔」 |

L1 對應需求書 §10.1「295 個 xUnit 測試」既有資產的延伸；L2 對應需求書 §4 互動規範；L3 集中收錄於[附錄 A](#附錄-a跨模組整合-l3-驗證劇本)。

### 0.4 模組依賴總覽

下圖標註功能模組之間的「**A 阻塞 B**」關係（A 未完成則 B 無法驗證）：

```
[基礎層 P0]
  §1.1 回合制 ──┬─→ §1.4 卡牌（Draw/Action 需要 TurnLoop）
              ├─→ §1.5 地圖（MapExpand 是回合階段）
              └─→ §1.11 持續效果（TurnEnd 計時）

  §1.2 角色 ──┬─→ §1.3 判定（屬性是擲骰加值）
            └─→ §1.7 同伴（同伴依賴角色資料結構）

  §1.5 地圖 ──→ §2.1 主地圖（渲染依賴 WorldMap 資料）

[擴充層 P1]
  §1.4 卡牌 ──┬─→ §1.6 ORBIT（事件卡進入軌道）
            └─→ §1.8 戰鬥（戰鬥卡為事件帶出）

  §1.6 ORBIT ──┬─→ §1.12 結局（結局卡走 ORBIT 機制）
             └─→ §1.9 訊息氣泡（事件提示來源）

  §2.1 主地圖 ──┬─→ §2.2 場景立繪（漂浮在玩家所在地塊）
              └─→ §2.3 小地圖（同步玩家位置與視野框）
```

## 1. 核心機制模組（對應需求書 §3）

### 1.1 回合制架構（對應需求書 §3.1）

**實作目標**
建立整局生命週期的主控迴圈：依 MapExpand → Draw → Action → EventCheck → TurnEnd 五階段循環推進，並在 TurnEnd 統一執行失敗條件檢查與自動存檔。

**設計重點摘要**（詳見需求書 §3.1）
- 每回合主角 AP 上限 **3**（重置非累積）；同伴每回合 **2 AP**（獨立計算）
- 主角 Draw 階段抽至手牌上限 **5**
- **首回合跳過 MapExpand**，玩家角色直接生成於序幕卡指定的初始地塊（4,4）
- **30 回合上限為失敗條件**，勝利條件改由結局卡（§3.4.5）負責
- 連鎖事件深度上限 **5 層**，同事件 ID 在同一 EventCheck 僅觸發 1 次
- 失敗條件三類：HP=0 重生失敗 / 回合 > 30 / 地圖飽和（連續 3 回合無合法區）
- **存檔/讀檔限制**：中途存檔/讀檔僅可在 Action 階段觸發；其他階段排隊至下一 Action

**Action 階段行動清單與 AP 規則**（詳見需求書 §3.1.4）

| 行動 | AP 消耗 | 觸發方式 |
|------|---------|---------|
| 移動 | **本回合累計第 1 格免費**，第 2 格起每格 1 AP | **Hover 已放置格 → 即時路徑預覽（連線 + 分段節點，綠=可付 / 紅=超 AP）→ click 直接走，每格 150ms 動畫**（v1.9 改）。AP 不足點紅色節點 → 拒絕並提示最遠可達；無路 → 提示「無路可達（v1.12：需 tag 相容 / 經橋接 tile）」。**v1.12 起**：BFS 含 tag 相容檢查，跨區強制走橋接 tile（如 `mansion-foyer` 同時 outdoor+indoor、`hidden-chamber` 同時 indoor+underground）|

### 1.5 地圖系統 11×11（v1.13 起；v1.12 前為 9×9。對應需求書 §3.5）

**實作目標**
維護 11×11 `WorldMap` 純資料結構，提供地塊放置、移動路徑計算、地塊變化（transformTile）三類操作，並透過事件通知所有渲染層（§2.1/§2.2/§2.3）。

**設計重點摘要**（詳見需求書 §3.5）
- 11×11 網格（v1.13 起；前 v1.12 為 9×9）；初始地塊固定中央 (5,5)，由序幕卡 `setupRules.initialTileId` 指定
- 合法放置區（v1.12 規則）：
  1. 與已放置地塊**4 方向相鄰**且未佔用的格（不含對角線）
  2. **Tag 配對**：候選 tile 之 `tags` 與所有 4 方向相鄰已放置 tile 之 `tags` 需兩兩 `TagsCompatible`（OR 邏輯：任一邊空 / 共享 1 個 tag → 相容）
  3. **Tag 中立橋接**：tile 的 `tags` 為空時視為通配（與任何相鄰皆相容）
  4. **批次選擇**：玩家從 `TileChoiceBatch` (≤ 3 張) 中視覺選 1 張為 held；可 re-select 互換或 Cancel 退原 slot
  5. **連續放置 GroupCount > 1**：1 張卡 = N 個 1×1 cell，玩家強制連續放完 N 格（同組共享 `GroupInstanceId`，第 2+ 格只看「同組已放格相鄰」+ 可選 GroupShape 拓撲限制 `rectangle:WxH` / `line:N`）
  6. **Cancel rollback**：放置中 cancel 時已放同組 cells 從 TileMap 移除、held 退回原 visual slot
- 移動規則（v1.12 規則）：
  - 4 方向；不允許旋轉地塊；事件僅在「停留」觸發，「經過」不觸發

### 1.8 戰鬥子系統（對應需求書 §3.8）

**實作目標**
實現完整 4 階段戰鬥流程（Encounter / PlayerTurn / EnemyTurn+Response / End），含 Reveal 機制、三種行動源、五級攻擊分級、玩家三反應、同伴輔助、vulnerable 狀態，並確保戰鬥結束後正確回到主回合 EventCheck。

**設計重點摘要**（詳見需求書 §3.8）
- **Phase A Encounter**：`2d6 + Skill(綠探索) + 足部 SkillBonus` vs `EncounterTn`；double6 強制 Advantage（Reveal=Full、玩家先攻）；double1 標記 vulnerable；Ambushed 首回合主角 AP=2
- **Phase B PlayerTurn**：補 AP 至上限 3；三種行動源：
  - **Basic**（5 種：Attack/Defend/Observe/Reposition/Retreat）— 每種每回合 1 次、無 AP
  - **Character**（角色 combatAbilities）— 每戰 1 次
  - **ActionCard**（手牌 combat 欄位）— 消耗 AP，使用後進棄牌堆
- **每戰鬥回合可執行多個行動**，僅受 AP 與各源次數上限限制；攻擊型 ActionCard 與 Basic Attack **互不干擾**（各自次數獨立計算）
- **Basic 動作細節**：
  - `Defend` — 本戰鬥回合 Dodge 加值 **+2**（單回合不累積，玩家方輪結束清零）
  - `Reposition` — Dodge 加值 **+1 累積**，戰鬥內**最多 +3**，戰鬥結束清零
  - `Observe` — 揭露敵方 1 個未知 EnemyAction（僅在 Reveal=None/Partial 時有意義）
  - `Retreat` — 結束戰鬥（結果為 EnemyFled，無戰利品）
- **Reveal 已知清單只增不減**：被使用過的 EnemyAction 自動加入 KnownEnemyActions；Observe 主動揭露 1 個；Reveal 等級本身不在戰鬥中升級
- **攻擊擲骰 5 級**：CritSuccess（傷害+3）/ Success（max(1, WeaponDamage+Power-Defense) × Multiplier）/ Partial（半傷）/ Fail / CritFail（標 vulnerable）
- **DamageMultiplier 上限 ×5.0**（多重來源連乘）
- **Phase C EnemyTurn**：依 trigger Priority + Weight 抽 EnemyAction；TargetingRule **連續 2 回合鎖同一目標 → 第 3 回合強制隨機其他目標**
- **Atk 計算**：`Atk = AttackPower + payload.damage`；若 EnemyPrepared → Atk × 2（蓄勢消耗）
- **AwaitingResponse**：同伴抵擋優先；無則玩家擇一 Accept / Dodge（1 AP）/ Block（1 AP，需盾）
- **Accept 反應**：全額受傷；**受傷後手牌 +1**（若手牌已達上限 5 則不抽）
- **Dodge 公式**：`2d6 + Skill + RepositionStack + DefendBonus(本回合)` vs Atk；double6 必定無傷；double1 必定全傷 + vulnerable
- **Block 公式**：`2d6 + Power + ShieldHitBonus` vs Atk；需副手裝備為盾，否則禁用
- **vulnerable**：受擊一次後消耗，+2 傷害（不疊加，stacking=replace；詳見 §1.11）
- **Phase D End**：Victory→LootEffects；EnemyFled→無戰利品；主角 HP=0→§1.10 重生擲骰
- **同伴 HP=0**：該場戰鬥退場，**戰鬥結束後以 1 HP 回歸隊伍**
- 戰鬥**不消耗主回合計數**

**實作方式建議**
- **Models**
  - `BattleState { Character Hero, List<NpcCompanion> Companions; BattleCard Card; int Round; RevealLevel Reveal; bool HeroVulnerable; List<string> KnownEnemyActions; HashSet<string> UsedCombatAbilities; HashSet<string> UsedBasicThisTurn; bool EnemyPrepared, EnemyDefending; CompanionId? PendingBlock }`
  - `enum RevealLevel { Full, Partial, None }`
  - `EnemyAction { string Id; EnemyActionKind Kind; TargetingRule Targeting; EnemyActionTrigger Trigger; int Weight; ActionPayload Payload }`
- **Services**
  - `BattleService.StartBattle(BattleCard)` — 建立 BattleState、執行 ResolveEncounter、進主迴圈
  - `BattleEngine.RunBattleLoop()` — 4 階段循環直到結束
  - `EnemyActionSelector.PickAction(state) → EnemyAction` — Priority 排序 + Weight 抽籤
  - `BattleService.RollAttack(action, state) → AttackResult` — 5 級分級
  - `BattleService.HandleResponse(ResponseChoice, state)` — Dodge/Block/Accept 分流
  - `BattleService.ApplyLootEffects(card, state)` — Victory 結算
- **Godot Node**
  - `scenes/battle/battle_scene.tscn` — 戰鬥子場景（§4.1 戰鬥 UI 留待 Phase 2 補設計）
  - 共用 `dice_panel.tscn`（§1.3）
- **資料來源**
  - `battle_card.json`（EnemyStats / EnemyActions / LootEffects）
  - `character.json`（combatAbilities）

### 1.11 持續效果系統（對應需求書 §3.11）

**實作目標**
統一管理裝備被動、buff/debuff、地塊環境效果三類持續效果：依 `triggerPhase` 觸發、依 `duration` 計時、依 `stacking` 模式疊加，並提供 `QueryActive` 給判定/戰鬥/移動等系統查詢當前修正值。

**設計重點摘要**（詳見需求書 §3.11）
- 觸發時機 7 種：onAcquire / drawPhase / actionPhase / eventCheck / turnEnd / onTileEnter / onCombatHit
- 計時 5 種：permanent / turns:N / phases:N / untilCondition / untilTrigger:N
- 疊加模式 4 種：**add**（疊加數值）/ **replace**（覆蓋）/ **max**（取大）/ **refreshDuration**（僅刷新時長）
- 條件支援：`enableCondition`（JsonLogic）；不滿足時**暫停效果但不移除**
- 背包中裝備效果**不計算**（與 §1.4 一致）
- 戰鬥外裝備被動：移除裝備才失效（permanent）
- vulnerable 採 `stacking=replace`（不疊加，受擊一次後消耗）

**實作方式建議**
- **Models**
  - `Effect { string Id; EffectTriggerPhase TriggerPhase; EffectDuration Duration; StackingMode Stacking; JsonElement? EnableCondition; List<EffectModifier> Modifiers; int RemainingTurns, RemainingTriggers }`
  - `EffectModifier { string Target /* moveCostOverride / rollCheckBonus / combatDamageBonus / incomingDamage … */, EffectOp Op, int Value }`
  - `enum StackingMode { Add, Replace, Max, RefreshDuration }`
- **Services**
  - `EffectsService.RegisterEffect(effect, sourceContext)` — 套疊規則由 stacking 決定
  - `EffectsService.QueryActive(target, jsonLogicCtx) → int` — 由 RollCheckService、MapService、BattleService 等呼叫
  - `EffectsService.TickPersistent(phase, jsonLogicCtx)` — 各階段統一呼叫；扣 turns/phases、移除過期、評估 untilCondition
  - `EffectsService.OnTriggerConsume(effectId)` — 由 BattleService 在受擊後呼叫，扣 untilTrigger 計次
- **資料來源**
  - 嵌在 `event.json` / `equipment.json` / `tile.json` 的 `effects` 子物件

### 3.5 地圖渲染架構優化路線（Phase 3 候選，對應需求書 §2.4 + §2.5）

**Context**

Phase 2 完成 Task 7（卡牌系統）+ Task 8 Stage 1（場景立繪）後，回顧地圖渲染架構（MainMap / Tile / 場景立繪）發現 4 個結構級議題；本節整理「現況 / 三方案 / Camera 重構 / 判讀」作為 Phase 3 重構候選依據。

**現況**

```
MainMap (Control)
├─ TileLayer (Node2D)
│  └─ Tile_r_c × 81 (TileVisual : Node2D + Polygon2D)
├─ ParallaxScene (Node2D, ZIndex=5)
├─ PlayCardZone (Control)
└─ Reset / Popup / MoveConfirmDialog (Control / Window)
```

- 無 `ClipContents`、無 `SubViewport`
- `CameraOffset` 為 float，但 `Projection.ProjectQuad` 使用 `(int)Mathf.Round(offsetRow)` → 拖曳時整格 snap
- 中鍵拖曳：[CameraController.cs](../scripts/Map/CameraController.cs)（`motion.Relative / 100px → CameraOffset`）
- 溢出 viewport 的 tile 靠相鄰 panel（LeftPanel / HandDock / RightPanel）視覺遮蓋

**三個架構級裁切方案**

| 方案 | 內容 | 對 Node2D tile 有效? | 工時 | 何時適用 |
|---|---|---|---|---|
| **A** | `MapArea.ClipContents = true` | ❌ Control 的 ClipContents 對 Node2D 子樹無效（tiles 是 `TileVisual : Node2D`）| 1 行 | 不適用本架構 |
| **B** | SubViewport 重構（`MapArea → SubViewportContainer → SubViewport → MainMapRoot`）| ✅ GPU 級 clipping，Node2D / Polygon2D 全部有效 | 4–8 小時 | 加 zoom / shader / post-processing 時 |
| **C** | Shader Discard（fragment shader 內 `discard` UV 越界） | ✅ 但需自訂 shader | 高 | tile 數量 >> 100，本案 81 格不適用 |

**Camera 重構選項**

- **平滑 sub-pixel 拖曳**：`CameraOffset` (float) 直接套到 `MainMapRoot.Position`，relRow 仍 int snap，視覺平滑（~2 小時）
- **Zoom（滑鼠中心）**：標準公式 `before/after ScreenToWorld + offset 修正`；scale 整個 `MainMapRoot`，**勿改 BaseTileSize**（會破 Projection）
- **慣性滑動**：對 TRPG 桌遊不適合（降低拖曳精準度）

**SubViewport 升級踩坑點**

| 風險 | 緩解 |
|---|---|
| 輸入座標需轉 viewport local | 用 `subViewport.GetMousePosition()` 取代 `mb.Position` |
| 拖曳手牌出牌（HandDock → PlayCardZone）跨 SubViewport 邊界 | Godot 4 drag-drop 需在同一 viewport — PlayCardZone 也搬進 SubViewport，或設計 wrap layer |
| `MoveConfirmDialog` 是獨立 Window | 不受影響，仍可正常顯示 |
| ParallaxScene 座標 | 與 tile 同 viewport 即可（搬進 MainMapRoot 一起 scale）|
| SubViewport 不自動 resize | 訂閱 `MapArea.resized` 同步 size |

**判讀與優先序**

| 優先 | 議題 | 根因 | 建議 |
|---|---|---|---|

### 5.1 模組系統與 manifest（對應需求書 §7.2）

**實作目標**
建立可熱重載的模組載入器，支援 `builtin/` 與 `user/` 兩個來源；啟動時掃描、Schema 驗證失敗則拒絕載入。

**設計重點摘要**（詳見需求書 §7.2）
```
modules/
├── builtin/
│   └── abandoned-mansion/    # 內建劇本
│       ├── manifest.json
│       ├── tiles/
│       ├── events/
│       ├── cards/
│       ├── characters/
│       └── art/
└── user/                      # 使用者自製模組（同結構）
```
- 啟動時掃描兩資料夾，依 `manifest.json` 載入
- 支援熱重載（開發模式）
- Schema 驗證失敗則拒絕載入並顯示錯誤

**實作方式建議**
- **Models**
  - `Module { string Id, string Name, string Author, string Version, ModuleSource Source /* Builtin/User */, string RootPath }`
  - `ModuleManifest { string Id, string Name, string Author, string Version, string PrologueFile, List<string> EndingFiles, List<string> EventFiles, ... }`
- **Services**
  - `core/modules/ModuleLoader.cs`
    - `ScanAll() → List<Module>` — 啟動時掃 `builtin/` 與 `user/`
    - `Load(modulePath) → ModuleLoadResult` — 解析 manifest、Schema 驗證、cache 內容
    - `EnableHotReload(Module)` — 開發模式 watch 檔案變動
  - `ModuleLoadResult { bool Success, Module? Module, List<string> Errors }`
- **熱重載**
  - 用 `System.IO.FileSystemWatcher` 偵測 `*.json` 變動
  - 變動時重新 Schema 驗證 + 重新 cache；ORBIT / WorldMap 中已使用的資料保留至下次切場才更新
- **錯誤處理**
  - Schema 驗證錯誤 → log 完整路徑與錯誤行號 → UI 主選單顯示「模組載入失敗」對話框（不直接崩潰）

### 5.2 10 支 JSONSchema 規格（對應需求書 §7.1）

**實作目標**
建立 10 支 JSONSchema 驗證所有模組資料；確保資料層與程式層的契約一致；新增 schema 時遵循統一模式。

**設計重點摘要**（詳見需求書 §7.1）

| Schema | 用途 | 對應 Model | 對應規格章節 |
|--------|------|----------|-----------|

| `event.json` | 事件卡（含 `triggerBattle`、`transformTile`） | `EventCard` | §1.4、§1.6 |

| `action_card.json` | 行動卡（含 `combat` 物件） | `ActionCard` | §1.4 |
| `equipment.json` | 裝備卡（含 `slotType` + `combatStats`） | `EquipmentCard` | §1.4 |

- **特殊欄位**
  - `transformations` 嵌入 `tile.json`（不獨立 schema）— 詳見需求書 §7.1 註
  - `condition` 欄位統一引用 `_common.json#/definitions/jsonLogic`

### 5.3 條件 DSL JsonLogic（對應需求書 §7.3）

**實作目標**
整合 `JsonLogic.Net` 套件作為條件評估器；建立統一的變數命名空間 context；提供熱重載安全與錯誤處理。

**設計重點摘要**（詳見需求書 §7.3）
- 採用 [JsonLogic](https://jsonlogic.com/) 業界開源規範 + `JsonLogic.Net` C# 實作
- 用於：地塊變化條件、ORBIT 揭露/觸發、事件選項條件、勝利/失敗條件
- **變數命名空間**：`flag.<name>` / `hero.{hp,ap,attr,equipment}` / `companion[i].{hp,id}` / `companion.count` / `turn` / `currentTile.{terrain,row,col,tileCardId}` / `tile[r,c].*` / `orbit.{A,B,C}.count` / `orbit.contains(<eventId>)` / `worldFlags.<name>`
- **支援運算符**：比較（== != < <= > >=）/ 邏輯（and or !）/ 算術（+ - * / %）/ 集合（in contains）/ 條件（if）/ 變數（var）/ 字串（cat）
- 條件評估失敗（變數不存在等）回傳 `false` 並 log warning
- 熱重載安全（純資料）

**實作方式建議**
- **Models**
  - `JsonLogicContext { Dictionary<string, object> Variables }` — 包裝所有變數
  - `core/services/JsonLogicEvaluator.cs`
    - `Evaluate(JsonElement rule, JsonLogicContext ctx) → bool`
    - `BuildContextFromGameState(GameState s) → JsonLogicContext` — 統一打包當前狀態
- **變數打包順序**（Build 時注入）
  1. `flag.*` ← `GameState.Flags` Dictionary
  2. `hero.*` ← `Character` 屬性、HP/AP、equipment 陣列
  3. `companion[i].*` 與 `companion.count` ← `Party.Companions`
  4. `turn` ← `GameState.Turn`
  5. `currentTile.*` ← `MapService.GetTileAt(playerPos)`
  6. `tile[r,c].*` ← lazy access via custom resolver
  7. `orbit.*` ← `EventOrbit` 統計
  8. `worldFlags.*` ← `GameState.WorldFlags`
- **錯誤處理**
  - 變數不存在 → 回傳 `false` + log（含原 rule 與缺失變數名）
  - 型別錯誤（如比較 string 與 int） → 回傳 `false` + log
- **效能**
  - 條件評估在 EventCheck / MapExpand 階段觸發，每幀不調用
  - Context build 一次後可重用（同階段多個條件用同 context）

**驗證方式 — L1 xUnit 自動化**
- [ ] `JsonLogic_AllSupportedOperators_ParsedCorrectly()`（所有運算符各一例）
- [ ] `JsonLogic_VariableHero_HpAndAttrResolved()`
- [ ] `JsonLogic_VariableContains_HeroEquipmentArray()`
- [ ] `JsonLogic_MissingVariable_ReturnsFalseAndLogsWarning()`
- [ ] `JsonLogic_TileTransformCondition_ForestAndFireFlag_True()`（需求書 §7.3.4 範例 1）
- [ ] `JsonLogic_HpRatioBelow30Percent_True()`（需求書 §7.3.4 範例 4）

**驗證方式 — L2 Godot 手動操作**
- [ ] 觸發地塊變化事件，確認條件評估正確（火災 → 焦土）
- [ ] ORBIT 事件揭露條件「探索 ≥ 4 且回合 ≥ 5」在第 5 回合且屬性符合時揭露
- [ ] 條件評估失敗（如手寫錯誤的 JSON）→ Godot console 出現 warning，不崩潰

### 5.4 存檔格式（對應需求書 §7.4）

**實作目標**
實作自動存檔（每回合 TurnEnd 1 次）+ 手動存檔（3 槽）；含完整 GameState 序列化與讀檔時機限制。

**設計重點摘要**（詳見需求書 §7.4）
- 格式：Godot `ConfigFile` 或 JSON（推薦 JSON 便於 debug）
- **自動存檔**：每回合 TurnEnd 階段 1 次（覆蓋自動存檔槽）
- **手動存檔**：3 槽，從 §4.2 區塊 #6 系統選項進入
- **手動讀檔時機**：
  - **主選單**：可直接進入「讀取存檔」
  - **遊戲中**：僅可在 **Action 階段**立即生效；其他階段排隊至下一個 Action
- **存檔內容必含**：
  - 當前 GameState 序列化（HP/AP/手牌/裝備/位置）
  - 回合數、隨機種子、模組 ID
  - **ORBIT 軌道狀態**（已揭/未揭、條件評估快照）
  - **地塊變化歷史**（哪些格子曾發生 transformTile）
  - **同伴 AI 內部狀態**（戰鬥輔助配置、AP 餘量等）
  - **重生擲骰使用狀態**（§1.10）
  - **持續效果清單**（§1.11，含剩餘計時）
  - **已揭露結局清單**（用於收集要素統計）

**實作方式建議**
- **Models**
  - `SaveSlot { int Index, SaveSlotType Type /* Auto/Manual1/2/3 */, DateTime SavedAt, string ModuleId, int Turn, byte[] PayloadJson }`
  - `SavePayload { GameState State, EventOrbitSnapshot Orbit, List<TileTransformHistory> Transforms, List<EffectSnapshot> Effects, ulong RandomSeed, List<string> RevealedEndingIds }`
- **Services**
  - `core/services/SaveService.cs`
    - `AutoSave()` — TurnEnd 呼叫，覆蓋自動存檔
    - `ManualSave(int slotIndex)` — 寫入手動槽
    - `Load(SaveSlot) → LoadResult` — 反序列化 + 還原所有狀態
    - `RequestLoad(SaveSlot)` — 遊戲中呼叫；Action 階段立即執行，其他階段排隊
- **存檔位置**
  - Windows：`%APPDATA%/HauntedManor/saves/`
  - macOS：`~/Library/Application Support/HauntedManor/saves/`
  - 用 Godot `OS.GetUserDataDir()` 取得
- **隨機種子**
  - `GameState` 持有 `RandomSeed` 與 `RngState`
  - 所有擲骰透過 `IRandom` 接口（依 seed 確定性）
  - 存檔時保存當前 RngState；讀檔還原

**驗證方式 — L1 xUnit 自動化**

- **涉及**：§1.1、§1.5、§1.12

### L3-07「事件變化地塊 → 場景立繪同步切換」
- **前置**：地塊 forest 含 transformations（火災事件 → scorched-earth）
- **步驟**：觸發事件 `fire-spreads` → EventCheck 套用 transformTile
- **期望**：主地圖紋理切換、小地圖色塊變灰棕、場景立繪三層 200ms 淡出 300ms 淡入新貼圖
- **涉及**：§1.5、§1.6、§2.1、§2.2、§2.3

### L3-08「事件連鎖 5 層上限」
- **前置**：構造事件鏈 A→B→C→D→E→F（每個觸發下一個）
- **步驟**：EventCheck 觸發 A
- **期望**：A~E 在本 EventCheck 處理；F 被推遲到下回合 ORBIT 最前端；連鎖計數歸零
- **涉及**：§1.1、§1.6

### L3-09「結局卡 reveal → trigger → 結束遊戲」
- **前置**：完美結局 `ending-perfect` 需 truth_revealed + survivor_rescued + 在 manor-entrance + escaped_before_storm
- **步驟**：完成所有旗標 → 移動到 manor-entrance → 觸發 escaped_before_storm
- **期望**：EventCheck 開頭 reveal、trigger 滿足升 A、立即結束遊戲進結局結算
- **涉及**：§1.6、§1.12

### L3-10「同伴抵擋傷害蓄勢」
- **前置**：同伴設定 supportType = BlockDamage
- **步驟**：戰鬥 Phase B 主角行動結束 → 同伴自動蓄勢「待命抵擋」（扣同伴 1 AP）→ Phase C 敵方攻擊
- **期望**：同伴代受全額傷害、蓄勢消除、不再扣 AP
- **涉及**：§1.7、§1.8、§1.11

### L3-11「事件 → 戰鬥 → 勝利 LootEffects → ORBIT 重評估」
- **前置**：事件 X 觸發戰鬥；事件 Y 條件為 `flag.boss_defeated == true`（B 類等待）
- **步驟**：觸發 X → 戰鬥勝利 → LootEffects 設 `flag.boss_defeated = true`
- **期望**：戰鬥結束後重評估 ORBIT，事件 Y 升 A、同 EventCheck 內被處理
- **涉及**：§1.4、§1.6、§1.8

### L3-12「戰鬥內主角 HP=0 → 重生成功 → 退回主場景 (4,4)」
- **前置**：序幕卡 respawnRoll.tn=7；首次重生
- **步驟**：戰鬥中主角 HP→0 → 戰鬥場景暫停 → 重生骰子動畫 ~2 秒 → 骰出 ≥7
- **期望**：戰鬥場景淡出 300ms、主場景淡入 500ms、主角位於 (4,4) HP=1、該戰鬥卡視為未完成
- **涉及**：§1.8、§1.10、§2.1

### L3-13「事件副作用 → 訊息氣泡 → 跳轉」
- **前置**：事件 push 訊息 `「ORBIT A1：書房鬼魂 將於 EventCheck 觸發」`
- **步驟**：玩家點擊氣泡圖示 → 列表展開 → 點該訊息
- **期望**：ORBIT 區塊 A1 槽位高亮 + 視窗滾動到該位置
- **涉及**：§1.6、§1.9

### L3-14「重生失敗 → 結局結算 → 主選單」
- **前置**：第 2 次 HP=0（首次已用過重生），或首次擲骰失敗
- **步驟**：HP→0 → 重生擲骰 / 跳過 → 失敗結局
- **期望**：失敗結局畫面顯示對應結局卡（如 ending-respawn-failed）+ 統計面板；玩家點「回主選單」 → GameState 清空、自動存檔保留
- **涉及**：§1.10、§1.12

### L3-15「裝備換裝 → 戰鬥內效果差異」
- **前置**：背包有兩把武器（A: WeaponDamage=3, B: WeaponDamage=5）
- **步驟**：先裝 A 進戰鬥打一發 → 退戰鬥換 B → 再進戰鬥打一發
- **期望**：兩次傷害公式套用對應 WeaponDamage；戰鬥內無法換裝（按鈕禁用）
- **涉及**：§1.4、§1.8、§1.11

### L3-16「30 回合上限失敗結局」
- **前置**：開新局，不完成任何旗標
- **步驟**：跑滿 30 回合（用 NEXT TURN 快速通過）
- **期望**：第 30 回合 TurnEnd 失敗條件檢查觸發失敗結局；統計面板顯示 0 旗標
- **涉及**：§1.1、§1.12

### L3-17「移動 → 主地圖動畫 + 場景立繪切換 + 小地圖玩家點同步」
- **前置**：玩家位於 forest 地塊
- **步驟**：移動到相鄰 water 地塊
- **期望**：主地圖 sprite 280–320ms 平滑插值；場景立繪舊三層淡出 200ms / 新三層淡入 300ms（含 water 中景水紋動效）；小地圖紅點同步移動到新格
- **涉及**：§1.5、§2.1、§2.2、§2.3、§2.4

### L3-18「地塊放置 → 三視角同步」
- **前置**：MapExpand 階段
- **步驟**：點持有地塊卡 → 點高亮合法格放置
- **期望**：主地圖翻牌動畫、小地圖新色塊出現、場景立繪不變（玩家未移動）；NEXT 預覽推進
- **涉及**：§1.4、§1.5、§2.1、§2.3、§2.4
