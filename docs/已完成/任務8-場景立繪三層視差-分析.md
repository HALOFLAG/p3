# 任務 8：場景立繪三層視差 — 實作可能性分析

**對應規格書章節**：§2.2 場景立繪三層視差 + §2.4 跨區塊整合
**對應需求書章節**：§5.2 / §5.4
**實作日期目標**：Phase 2 第二優先（Task 7 後）

---

## 1. 任務目標摘要（規格書 §2.2）

> 在玩家所在地塊上方渲染 300×140 px 的三層視差場景立繪（遠/中/近），地塊切換時淡入淡出，依地形類型套用動態效果（水紋、葉動、雲飄、夜濾鏡）。

關鍵指標：
- **框體**：300×140 px、金色 1.5px 邊框、**持續漂浮在玩家所在地塊上方**
- **三層位移比例**：far 0.1× / mid 0.5× / near 1.0×；觸發來源是**滑鼠位置**
- **美術尺寸**（含 10–20 px 外擴給視差留 buffer）：
  - far 320×90
  - mid 320×110
  - near 320×140
- **切換動畫**：舊三層 200ms 淡出 → 新三層 300ms 淡入 → 視差位移重置
- **動態效果**：water 中景水紋 sin 波 / forest 葉片搖擺 / mountain 雲層飄移 / night 深藍濾鏡

## 2. 使用者參考圖分析

### `場景立繪(1).png`（同資料夾）
顯示的是「玩家中心 + 4 個相鄰地塊」的俯瞰透視圖。中央偏上有一個**有縱深的小型立繪劇場**，內容為：
- **後牆（far 層）**：森林背景插圖 + 上方標牌「森林小徑」
- **中層（mid 層）**：兩個角色立繪（紅袍、綠袍）
- **前緣（near 層）**：劇場地板含花朵、石頭等前景元素
- **整體**：劇場像一個「打開的紙箱」立在玩家地塊上，與規格書的 300×140 框完全吻合，只是**圖中以 3D 立體感呈現該框內容**

### `場景立繪(2).png`（同資料夾）
是同一立繪的「分解圖」，把它拆成 5 個獨立部件：
- 完整組合圖（左側）
- 後牆 + 標牌（右上）
- 角色 1 個 / 角色 2 個（右中）
- 含花朵的地板帶（右中下）
- 地板基礎（右下）
- 純森林背景作為「地塊面」（最下方）

→ 這正是規格書要求的 **far / mid / near 三層 + 邊框 + 標牌**的實際視覺分解，差別只在使用者畫了立體透視效果。

### 與規格書對照

| 元件 | 規格書 | 參考圖 | 結論 |
|---|---|---|---|
| 框尺寸 | 300×140 | 立體劇場（投影後≈該大小） | ✓ 一致 |
| 遠層 | forest 背景 | 後牆森林插圖 | ✓ **使用者決策：裁切該地塊卡上半部（圖案 + 名稱）作為遠景** |
| 中層 | 角色 / 主視覺 | 兩個角色 | ✓ 比規格更具體（NPCs） |
| 近層 | 動態前景 | 花朵 / 石頭地板 | ✓ 一致 |
| 邊框 | 金色 1.5px | （參考圖未顯示邊框） | 用規格書 |
| 標牌 | 規格書未提 | 「森林小徑」標牌 | ✓ **內含於 far 層裁切（地塊卡上半部已含名稱）**，免另做 |
| 立體感 | 平面三層視差 | 立體劇場感 | ⚠ 取捨：純 ParallaxBackground 是 2D，3D 感需另做 |

### 🔑 關鍵設計：遠景 = 地塊卡上半部裁切

使用者決策：**遠景圖直接用該地塊的卡牌 PNG（[art/tiles/forest.png](../art/tiles/forest.png) 等），裁切其上半部（含插圖 + 名稱橫幅）作為 far 層**。

帶來的影響：
- **美術需求從 18 張 → 12 張**（far 層完全免做，從既有 6 張 tile PNG 取上半即可）
- **標牌「森林小徑」自動顯示**：因為地塊卡的 PNG 上半部本來就有名稱橫幅，裁切後直接帶過來，不再需要獨立 Label 對映
- **視覺一致性**：場景立繪的遠景跟玩家正踩著的地塊面是「同一張圖的不同部分」，提供「就是這片森林」的直覺連結
- **實作技術**：Godot 用 `AtlasTexture`（指定 region 為 PNG 上半 50%）或 `Sprite2D.RegionEnabled = true` 即可，零美術成本

```
art/tiles/forest.png（完整地塊卡）
┌─────────────────────┐  ← 上半（far 層用：插圖 + 「森林小徑」橫幅）
│   森林小徑          │
│  [森林插圖]         │
│                     │
├─────────────────────┤  ← 中分線
│  [stats / 描述]     │  ← 下半（地塊上不顯示，只用於 hover 之類）
└─────────────────────┘
```

## 3. 實作方式選項

### 方案 A：規格書原案（純 2D 三層 ParallaxBackground）

- 用 Godot 內建 `ParallaxBackground` + 3 個 `ParallaxLayer`（GPU 加速、規格書 §3.4 明列）
- 每地形 3 張 PNG（far/mid/near），共 6 種地形 × 3 = **18 張美術**
- 滑鼠位置驅動 motion_offset，三層位移比例 0.1 / 0.5 / 1.0
- 框體用一個 `Panel` + 金邊 stylebox 包住 ParallaxBackground

**優點**：
- 完全照規格書、效能最好（GPU）
- 實作最快（核心程式約 150–200 行）

**缺點**：
- 純 2D 平面感，沒有參考圖的「立體劇場」深度
- 視覺豐富度受限於 PNG 美術的精緻度

### 方案 B：擬 3D 立體劇場（仿參考圖立體感）

#### 詳細結構
劇場像一個「半開的紙箱」：後牆向後傾、地板向前傾、可選的左右側牆。

```
            ┌───────────┐         ← 後牆（far 層 = 裁切的地塊卡上半，含名稱）
           /│  森林小徑  │\
          / │  [插圖]   │ \       ← 後牆向後傾斜（呈梯形，上窄下寬）
         /  └───────────┘  \
        /  ┌───────────┐   \    ← 中層：角色 sprite（billboards 永遠面向相機）
       /   │ 紅袍 綠袍  │    \
      └────┼───────────┼─────┘   ← 地板向前傾斜（呈梯形，上窄下寬，正好相反）
           │ 花花石頭   │            含 near 層動態前景
           └───────────┘
```

#### 實作細節
- **後牆**：用 `Polygon2D` 4 角梯形（沿用 [core/Map/Projection.cs](../core/Map/Projection.cs) 的 `ProjectQuad`，但用較陡的傾斜參數；UV 對應裁切的 tile PNG 上半）
- **地板**：另一個 `Polygon2D` 梯形，方向反轉（上窄下寬，但梯形「在下」）；貼 near 層 PNG（花朵 / 石頭）
- **可選的左右側牆**：兩個 `Polygon2D` 三角形或薄梯形，半透明 Brown 色塊做「箱子側面」陰影
- **角色 sprite**：1–3 個 `Sprite2D` 站在地板「中段」位置，固定面向相機（Billboard 效果）
- **滑鼠視差**：滑鼠位置驅動「相機虛擬偏移」 → 後牆和地板的 4 角座標微調，左右兩邊偏量不對稱（給出視差感）
- **動態效果**：water 後牆 sin 波 shader / forest 葉片 sprite 隨機 sway / mountain 後牆雲層 horizontal scroll / night ColorRect overlay

#### 優點
- ✅ 視覺最忠於使用者參考圖（真有縱深的立體劇場感）
- ✅ 與既有地塊傾斜風格（§5.1）統一 — 用同一套 `ProjectQuad` 數學
- ✅ 美術需求最少（後牆免做、地板可程式繪）
- ✅ 與「玩家踩著的地塊」視覺連動：後牆和正下方那張地塊卡用同一張 PNG，渾然一體

#### 缺點
- ❌ 不能用內建 `ParallaxBackground` → 違反規格書 §3.4「ParallaxBackground GPU 加速」明列建議
- ❌ 自製透視投影 + 滑鼠驅動的偏移邏輯複雜度高（300–400 行程式）
- ❌ Polygon2D 動態 UV + 相機偏移 + 動畫的同步處理容易出 bug
- ❌ 無法直接套用 Godot `AnimationPlayer` 的 ParallaxLayer 預設動畫，需手動 Tween
- ❌ 切換地塊時的淡入淡出涉及多 Polygon2D 同時 modulate，協調性差
- ❌ 偵錯困難：自製透視矩陣 / 4 角座標 inspector 看不到視覺問題
- ❌ 測試覆蓋不易（純 Godot 表現層 + 自製數學 = L1 自動測試難寫）

#### 適用場景
- 美術預算極低（不想做 mid 層 character / near 層 ground PNG）
- 視覺立體感是最高優先（高於程式維護成本）
- 開發團隊對 Godot 自製 transform 數學熟悉

### 方案 C：混合 — 2D Parallax + 「立繪框」做立體框感（推薦）

#### 詳細結構
框體本身是 2D 的 Panel + 金邊，但**框的設計**模仿劇場（頂部帶標牌橫幅、下方稍微擴大暗示舞台前緣）。框內裝 ParallaxBackground 三層。

```
┌─🟨 森林小徑 🟨─┐    ← 框頂含標牌橫幅（已內建於 far 層的裁切上半部）
│  ┌──────────┐  │    ← 金色 1.5px 邊框（規格書要求）
│  │  [森林]  │  │    ← far 層：裁切的地塊卡上半（PNG region）
│  │  [角色]  │  │    ← mid 層：character sprite + 動態
│  │  [前景]  │  │    ← near 層：花朵 / 石頭 + 動態
│  └──────────┘  │
└─────────────────┘
   下緣金邊稍微外擴模擬舞台前緣
```

#### 實作細節
- **框體**：`Panel` + StyleBoxFlat（Gold 1.5px 邊 + Paper 底，重用 [Palette](../scripts/Ui/Theme/Palette.cs)）
- **框內**：`ParallaxBackground` 節點，包 3 個 `ParallaxLayer`：
  - far ParallaxLayer：`motion_scale = (0.1, 0)`，內含 `Sprite2D` 設 `RegionEnabled = true`，region 為 tile PNG 上半（裁切）
  - mid ParallaxLayer：`motion_scale = (0.5, 0)`，含 character sprite（v1 程式生成色塊 placeholder）
  - near ParallaxLayer：`motion_scale = (1.0, 0)`，含前景動態
- **滑鼠視差**：`_Process(delta)` 讀 `GetGlobalMousePosition() - center` → 設 `ParallaxBackground.scroll_offset`
- **切換動畫**：地塊變更時 → 整個 ParallaxBackground modulate.a 1→0 (200ms) → 換三層 Texture → modulate.a 0→1 (300ms)
- **動態效果**：
  - water：mid 層 `Sprite2D.position.y` Tween sin 波 loop
  - forest：near 層加 1–2 個小葉片 sprite，Tween 隨機 rotation 抖動
  - mountain：far 層之上疊一層 ParallaxLayer 雲圖，水平 scroll loop
  - night：整個 Panel 之上加 `ColorRect` 深藍 modulate 0.3 alpha
- **角色立繪（Stage 3 nice-to-have）**：mid 層加 1–N 個半透明 sprite，從 `WorldMap.Companions` 取 portrait 路徑

#### 優點
- ✅ 完全照規格書 §3.4 走（`ParallaxBackground` GPU 加速）
- ✅ Godot 內建 `ParallaxBackground` 處理 motion_scale 和 wrap，**無需自製數學**
- ✅ 程式量適中（150–250 行），維護成本低
- ✅ 視覺接近參考圖：金邊框 + 標牌（內含於裁切上半）+ 三層視差 = 「半立體劇場感」
- ✅ 動態效果直接綁 `AnimationPlayer` 或 `Tween`，無 transform 同步問題
- ✅ 切換 Tween 用單一 modulate 處理，俐落
- ✅ Inspector 可視所有節點 / Texture，偵錯容易
- ✅ 可分階段交付：Stage 1 用 placeholder 骨架可 F5 跑、Stage 2 補美術、Stage 3 加角色
- ✅ 與規格書 L2 驗收項一一對應

#### 缺點
- ❌ 仍是 2D 平面感，沒有方案 B 真透視的立體深度
- ❌ 「劇場感」主要靠框體設計（標牌 + 金邊）+ 視差層位，不像 B 那樣後牆斜出來
- ❌ 比方案 A 多 ~80 行（標牌 + character sprite）

#### 適用場景
- 規格書 §3.4 要求嚴格遵守
- 性能優先（GPU 加速）
- 開發時程緊（Stage 1 即可交付雛形，再依美術 / 工時補 Stage 2/3）
- 美術預算可滿足 mid + near 層 6 張 PNG

### B 與 C 直接比較

| 面向 | 方案 B（擬 3D 立體劇場） | 方案 C（2D Parallax + 立繪框） |
|---|---|---|
| **渲染方式** | 多 Polygon2D + 自製透視 4 角投影 | Panel + ParallaxBackground + 3 ParallaxLayer |
| **效能** | 中等（每幀重算 4 角 + 多 Polygon2D） | 高（GPU 加速 + Layer 間獨立） |
| **規格書 §3.4 遵守** | ❌ 違反（不用 ParallaxBackground） | ✅ 完全照做 |
| **程式量** | ~300–400 行 | ~150–250 行 |
| **複雜度** | 高（透視矩陣 / 滑鼠 → 4 角換算 / Tween 多 sprite 同步） | 中（Godot 內建 + 訂閱 + 1 個 Tween） |
| **視覺立體感** | ⭐⭐⭐⭐⭐ 真 3D 透視 | ⭐⭐⭐ 半立體（框 + 視差） |
| **美術需求** | 最少：far 層裁切重用、地板可程式繪、角色 sprite 6 個 | 中等：far 層裁切重用、mid + near 各 6 = 12 PNG |
| **動態效果** | 自製 Tween 處理 sprite 動畫 | `AnimationPlayer` 直接綁 ParallaxLayer |
| **切換淡入淡出** | 多 Polygon2D 同步 modulate（協調性差） | 整個 ParallaxBackground 一次性 modulate（俐落） |
| **偵錯** | 自製數學 + 4 角座標難 inspect | Godot inspector 看每個 layer / sprite |
| **Stage 拆解** | 不易（需先建立 3D 透視框架才能跑） | 易（Stage 1 placeholder 即可動，後續補美術） |
| **與既有 §5.1 一致** | ✅ 用同一套 ProjectQuad 數學 | ✗ 各自獨立 |
| **後續擴充（戰鬥場景背景）** | 較難（透視框架不易共用） | 容易（mid 層 PNG 可直接拿來當戰鬥背景） |
| **L1 自動測試** | 困難（純 transform 表現層） | 困難（同上）— 兩者皆無法測 |
| **L2 驗收覆蓋率** | 全部可覆蓋，但 dynamic effect 工程量大 | 全部可覆蓋，dynamic effect 直接套 Godot 機制 |
| **總工時** | ~10–12 小時 | ~6.5–7 小時 |
| **總美術工時** | mid 6 張 + 角色 6 個 = ~10 小時 | mid + near 共 12 張 = ~12 小時 |

### 如何選擇

**選 B 如果**：
- 視覺立體感是 **最高 priority**，遠超過開發時程 / 維護成本考量
- 開發團隊對 Godot 2D 透視 transform 數學熟悉、有信心
- 願意接受規格書 §3.4 違反 + L1 測試空窗
- 美術專注於角色 sprite（mid + 場景前景就交給程式做）

**選 C 如果**（推薦）：
- 想要規格書合規 + 性能 + 維護成本三優先
- 開發時程緊張，希望 Stage 1 placeholder 就能 F5 看效果
- 美術可以給足 12 張 PNG（mid + near × 6 terrain）
- 接受「框體立體感模擬」而非真 3D 透視
- 將來可能擴充戰鬥場景背景（PNG 可直接重用）

## 4. 推薦路徑：方案 C（漸進式三階段）

### Stage 1：技術骨架（無新美術，可立即做）
1. 建 `scenes/map/parallax_scene.tscn`：
   - 根 `Control` 節點 300×140
   - 子 `Panel` 金邊 stylebox（重用 [scripts/Ui/Theme/UiTheme.cs](../scripts/Ui/Theme/UiTheme.cs) 的 Gold + Ink）
   - 子 `ParallaxBackground` + 3 個 `ParallaxLayer`（motion_scale 0.1 / 0.5 / 1.0）
2. 建 `scripts/Map/ParallaxSceneController.cs`：
   - 訂閱 `MainMapRenderer.PlayerPositionChanged`（已存在）
   - 從 `WorldMap` 讀玩家當前地塊 terrain
   - **far 層**：`Sprite2D.Texture = art/tiles/{terrain}.png`、`RegionEnabled = true`、`RegionRect = (0, 0, w, h/2)` ← 裁切上半
   - mid/near 層暫用程式生成色塊 placeholder（v1）
   - `_Process(delta)`：算 mouse 位置，套 `ParallaxBackground.scroll_offset`
3. 在 `MainBootstrap` 把 `parallax_scene.tscn` 加為 `MapArea` 子節點，動態定位到玩家地塊上方（用 `Projection.ProjectQuad` 取 player 格座標）
4. **現有 280+ 測試不受影響**（純 Godot 表現層，無 core/ 變動）

**交付物**：規格書 L2 驗收的前 4 項（漂浮、滑鼠視差、淡入淡出基礎、地形切換 + 自帶名稱橫幅）。

### Stage 2：美術 + 動態效果
1. 補 **12 張地形 PNG**（mid/near × 6 terrain，**far 層免做**因為直接從 tile PNG 裁切）
2. 加入 `AnimationPlayer` 為各地形配動態：
   - water：mid 層 sin 波 shader 或 position offset loop
   - forest：near 層葉片 sprite 隨機 sway（Tween chain）
   - mountain：mid/near 雲層 horizontal scroll loop（far 為 tile 上半，不便 scroll）
   - night：整體 ColorRect overlay 深藍 modulate
3. 切換時 Tween 0/1 modulate（淡出 200ms → 換 Texture region / mid / near → 淡入 300ms）

**交付物**：規格書 L2 驗收項 5、6（dynamic effects + night filter）。

### Stage 3：同伴顯影（仿參考圖）
**標牌已內建於 far 層裁切的上半部，本階段免做**。

1. mid 層加 `WorldMap.Companions.Count` 個半透明 64×96 sprite，沿框寬均分位置
2. 同伴更換 / 死亡時 sprite 淡入淡出
3.（可選）地形未對應到地塊卡時的 fallback：用程式繪一個 Label 顯示 terrain enum 名稱

**交付物**：使用者參考圖的「立體劇場」感（雖然仍是 2D parallax）。

## 9. 結論與建議優先序

### 結論
- **方案 C（混合：規格書 ParallaxBackground 主幹 + 立繪框 + 標牌 + 同伴顯影）為最佳**
- 與使用者參考圖意圖最貼近，技術上仍走 Godot 內建路徑（效能、效率）
- 可分 3 階段交付，Stage 1 即可看到雛形

### 建議
1. **先進 Stage 1**：純技術骨架，無新美術依賴。完成後即可 F5 驗證視差與切換。
2. **美術產製平行進行**：18 張 PNG 是主要瓶頸，建議在 Stage 1 期間以 placeholder 先跑通流程，美術完成後直接替換。
3. **標牌 + 同伴顯影**列為 Stage 3 的「nice to have」，不影響規格書原始驗收。
4. 與下一個任務（任務 9 ORBIT 軌道板）解耦良好 — Task 8 動到的檔案（parallax_scene、ParallaxSceneController）與 Task 9 的事件系統互不相干，可並行。
