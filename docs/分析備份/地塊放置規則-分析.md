# 地塊放置系統綜合分析（Phase 3 / 4 候選）

> 對應規格書 §1.5 / §3.1.4 / §3.5。本文件記錄六項地塊系統候選改造，皆為玩家測試後提出：
> 1. **Tag 配對 + 中立橋接** 放置規則
> 2. **「3 張選 1」批次選擇** 抽牌機制
> 3. **Prologue 自定義 tileBatches** 模組作者控制節奏
> 4. **多尺寸 tile**（1×2 / 2×1 / 2×2 / 3×1 等）視覺與資料結構擴展
> 5. **地塊組（連續放置）**：1 張卡 = N 個 1×1 tile，玩家強制連續放完
> 6. **縫隙裝飾層**：已放 tile 之間的 push-apart gap 內畫裝飾紋理
>
> 1+2+3+5 互相依賴 → 建議 Phase 3 v1.12 整合一次完成。
> 4 與 1-3 解耦 → 建議延 Phase 4 任務 22 補上（不影響當前模組）。
> 6 純視覺（不影響邏輯）→ 建議 Phase 3 任務 15（美術替換）一併進行。

## A 部分：Tag 配對放置規則

### A.1 規則摘要 — v1.12 完整放置規則整合視圖

> 本節為**所有規則層的統合視角**，作為實作時的權威 reference。各層深入展開於後續章節。

#### 規則架構：三層判定（依序檢查，全通過才放置）

```
┌─────────────────────────────────────────────────┐
│  Layer 1：基本約束（既有，永遠檢查）              │
│   ├─ 邊界內（9×9）                              │
│   ├─ 該格未被占用                                │
│   └─ 與已放置 tile 4 方向相鄰（上下左右，非對角）│
└─────────────────────────────────────────────────┘
                    ↓ 全部通過才進
┌─────────────────────────────────────────────────┐
│  Layer 2：Tag 配對（A 部分新加）                 │
│   候選 tile tags 與相鄰 tile tags 須有相容       │
│   相容條件（任一即可，OR 邏輯）：                │
│   ├─ 候選 tags 為空 → 中立橋接（永遠相容）       │
│   ├─ 相鄰 tags 為空 → 通配符（視為相容）         │
│   └─ 雙方共享至少 1 個字串                       │
└─────────────────────────────────────────────────┘
                    ↓ 通過才進
┌─────────────────────────────────────────────────┐
│  Layer 3：組放置約束（D' 部分，僅 GroupCount>1） │
│   第 1 格 → 上面 Layer 1+2 規則                  │
│   第 N 格（N≥2）：                                │
│   ├─ 必須相鄰已放同組格（4 方向）                │
│   ├─ 不檢查場上其他 tile（已透過第 1 格進場）    │
│   └─ 若 groupShape 指定 → 限定下一格位置         │
└─────────────────────────────────────────────────┘
```

#### 完整流程（玩家視角）

```
[模組載入] ModuleLoader 解析 prologue.tileBatches
  ├─ 起始格 (4,4) = village-square 直接放
  ├─ 剩餘 tile 依 module 作者規劃進 PendingTileBatches 序列
  └─ 沒寫 batches → fallback 機械抽 3 張

[每回合 MapExpand 階段]
  Step A：BeginMapExpand
  ├─ TileChoiceBatch 為空？
  │   ├─ 是 + PendingTileBatches 非空 → 取下一組（如 ["mansion-foyer"]）
  │   ├─ 是 + PendingTileBatches 空 → fallback 抽 deck 頂 3 張
  │   └─ 都空 → 階段跳過（無 tile 可放）
  └─ 非空 → 直接進選擇

  Step B：玩家從 RightPanel slot 1/2/3 選 1 張
  └─ SelectFromBatch(idx) → HeldTileId = 該 tile

  Step C：（若 GroupCount>1）進入「組放置模式」
  ├─ 分配 GroupInstanceId（流水號）
  ├─ PendingGroupRemaining = GroupCount
  ├─ slot 顯示「儀式廳 (1/4)」
  └─ 否則直接進 Step D

  Step D：主地圖高亮合法格（依 Layer 1+2+3 規則）

  Step E：玩家點目標格 → TryPlaceHeldTile
  ├─ 若是組第 N 格（N<GroupCount）→ 繼續放（slot 顯示 N+1/M）
  ├─ 若是組第 GroupCount 格 → 組完成（GroupInstanceId 永久寫入 PlacedTile）
  ├─ 若 GroupCount=1 → 普通放置完成
  └─ 完成後 batch 自動移除該 tile

  Step F：（可選）Cancel
  ├─ 普通 tile：HeldTileId 退回 batch 末尾
  └─ 組進行中：所有已放格從 TileMap 移除 + tile 退回 batch
```

#### 7 個獨立規則層的職責

| 規則層 | 職責 | 來源章節 |
|---|---|---|
| **基本約束** | 邊界 / 未占用 / 4 方向相鄰 | 既有（規格 §1.5）|
| **Tag 配對** | 候選 tile 與相鄰 tile tag 至少共享 1 個 | A 部分（A.2-A.3）|
| **批次來源** | 玩家只能放當前 batch 中的 tile | B 部分 |
| **批次補充** | batch 空才補；優先 prologue 定義，否則 fallback 機械抽 3 | B + C 部分 |
| **組連續放置** | GroupCount>1 必連續放完；同組格相鄰；可選 groupShape | D' 部分 |
| **區塊識別** | 同次放置共享 GroupInstanceId；視覺金邊外框 | D'.12 |
| **移動 tag** | 移動相鄰格也須 tag 配對（強制經橋接）| D'.13 |

#### Tag 配對核心邏輯（OR 邏輯，三個相容條件）

```
目標格必須與至少一個已放置地塊正交相鄰（上下左右）

候選地塊與相鄰地塊的 tags 須滿足下列任一條件：
  - 候選地塊 tags 為空 → 中立橋接，可置於任何相鄰空格
  - 相鄰地塊 tags 為空 → 相鄰中立地塊視為通配符
  - 雙方 tags 至少共享一個字串

不符合時 UI 該格不會亮起，亦無法以鍵盤／API 強制放置
```

#### IsLegalPlacement 完整決策樹

```python
def IsLegalPlacement(row, col):
    # Layer 1: 基本約束
    if not IsInBounds(row, col): return False
    if TileMap[(col,row)] is not None: return False  # 已占用

    # Layer 3a: 組進行中？走不同分支
    if state.PendingGroupCells.Count > 0:
        # 組第 2 格起：只檢查同組相鄰
        if not IsAdjacentToPendingGroup(row, col): return False

        # 若有 groupShape，還要檢查形狀
        if tile.GroupShape is not None:
            expected = ComputeNextShapeSlot(...)
            if (col, row) != expected: return False

        return True  # 組進行中通過

    # Layer 1 (續): 第 1 格須 4 方向相鄰已放置 tile
    if not HasPlacedNeighbor(row, col): return False

    # Layer 2: Tag 配對（state-mode 才檢查；standalone fallback）
    if state is None or module is None: return True

    candidate_id = state.CurrentPlayer.HeldTileId
    if candidate_id is None: return False

    candidate_tags = module.Tiles[candidate_id].Tags
    return AnyNeighborTagCompatible(row, col, candidate_tags)
```

#### 規則互動觀察

**觀察 1：放置規則 + 移動規則 = tag 連通閉環**
- 放置規則保證**靜態相鄰**有 tag 共享
- 移動規則（D'.13）保證**動態通行**檢查同樣規則
- 整體效果：tile 群依 tag 自然分區，玩家被引導走「連通鏈」

**觀察 2：組規則繞過外部 tag 檢查**
- 組第 2 格起只看「同組相鄰」，不看場上其他 tile
- 同組格 tag 永遠相同（同 tile），組內格相互合法是顯然
- 但**整組進場**仍需透過第 1 格與場上 tag 配對 → 不影響整體 tag 邏輯

**觀察 3：組合卡與 batch 的耦合**
- 一張組合卡（如 ritual-hall GroupCount=4）在 batch 中佔 **1 個 slot**
- 玩家連續放 4 格 = 消耗 1 張卡
- batch 視覺上 slot 計數不變，但「儀式廳 (3/4)」進度顯示玩家進度

**觀察 4：1 張組設計威力（C 部分）**
- prologue.tileBatches 寫 `["mansion-foyer"]` 單張組
- 玩家**必須在這回合放下 mansion-foyer**（無其他選擇）
- 強制敘事節點，玩家無法跳過橋接 tile

## B 部分：「3 張選 1」批次選擇機制

### B.1 規則摘要

- 進入 MapExpand 階段，玩家從**最多 3 張**候選中選 1 張放置
- 批次內未選的 tile **保留到下回合**（不捨棄）
- 批次清空後，下次 MapExpand 抽取下一組（最多 3 張，deck 不足時取剩餘 1-2 張）

### B.2 順序與資料結構（緊湊模式 List）

**TileDeck（既有，不變）**：純 `List<string>` 線性序列，不洗牌

**TileChoiceBatch（新增）**：採緊湊模式 `List<string>`

```
[初始]
deck = [A, B, C, D, E, F, ...]
batch = []

[回合 1 BeginMapExpand]
batch 空 → 從 deck 頭抽 min(3, deck.Count) 張：
  batch = [A, B, C]
  deck = [D, E, F, ...]
slot1=A / slot2=B / slot3=C

[玩家點 slot 2 = SelectFromBatch(1)]
  selected = batch[1] = B
  batch.RemoveAt(1) → batch = [A, C]
  HeldTileId = B
slot1=A / slot2=C / slot3=空

[玩家放 B 到地圖] → HeldTileId=null, batch 不變

[回合 2 BeginMapExpand]
batch 仍有 [A, C]，跳過抽取

[Re-select 玩家點 slot 1（A）= SelectFromBatch(0) 後又改點 slot 1（C）]
  第一次：selected=A, batch=[C], HeldTileId=A
  第二次：selected=C, batch.RemoveAt(0) → batch=[]
          prev HeldTileId=A → batch.Insert(0, A) → batch=[A]
          HeldTileId=C
slot1=A / slot2=空 / slot3=空（C 變持有，A 退回 slot 1）

[Cancel 退回]
  prev HeldTileId=C → batch.Add(C) → batch=[A, C]
  HeldTileId=null
```

**關鍵行為**：
- **slot 越用越少，從左對齊補位**（仿桌遊「打出一張剩下中央靠攏」）
- **Re-select 時 prev held 退回該 slot 位置**（保 slot 順序穩定）
- **Cancel 時 held 退回末尾**（不影響其他 slot）
- **「全部放完」= batch.Count == 0**（清楚的補充觸發條件）

## C 部分：Prologue 自定義 tileBatches

### C.1 動機

「機械抽 3 張」雖簡單，但失去**敘事控制**。模組作者可能希望：
- 第 1 組就是「村莊區 2 張」（建立基礎）
- 第 2 組「橋接 tile 1 張」（強制特定時機推進劇情）
- 第 3 組「危險區 3 張」一起出現

需要 schema 讓作者**指定批次內容與順序**。

### C.2 三方案對比

| 方案 | 描述 | 優點 | 缺點 |
|---|---|---|---|
| **A** ★ | 序幕卡 `prologue.tileBatches: [[id,...], ...]` | 集中、敘事控制力強、自然延伸既有 prologue 結構 | 模組作者要設計批次節奏 |
| **B** | tile.json 每個 tile 加 `batchGroup: int` | 散在各檔 | 看不出整體節奏，需 ≤3 張限制要 cross-tile 驗證 |
| **C** | 獨立 `tile_batches.json` | 隔離管理 | 增加檔案數，與 prologue 邏輯分散 |

**推薦 A（序幕卡定義）**。

### C.5 設計威力 — 「1 張組」當敘事節點

**1 張組**強制玩家：
- 第 4 組 `mansion-foyer` 一張：玩家**必須先開橋接 tile** 才能進洋房（戶外與室內無第二橋接）
- 第 7 組 `upstairs-corridor` 一張：強制玩家此時注意「危險升級」（rollCheck TN10 onEnter）
- 玩家無法「跳過敘事節點」— 設計者完全控制故事推進時機

### C.6 驗證規則（schema）

```
- 每組 1-3 張
- 每個 tile id 必須在 module.Tiles 中存在
- 各 tile 出現次數 = module.Tiles[id].Copies（不多不少）
- 起始格 (startingTileId) 不在 tileBatches 中（已直接放 4,4）
- batches 順序 = 抽取順序（第 1 組先用，最後 1 組最後）
```

`ModuleLoader` 啟動時驗證，失敗 throw exception。

### C.7 向後相容

- **新模組**：寫 `prologue.tileBatches` → 走批次定義
- **舊模組（沒寫）**：fallback 到「機械抽 3 張」（B 部分草案）
- **standalone（xUnit）**：保留既有 1 張行為

```csharp
public bool BeginMapExpand()
{
    ...
    if (_state.TileChoiceBatch.Count == 0)
    {
        // v1.13：優先用模組定義的下一組
        if (_state.PendingTileBatches.Count > 0)
        {
            _state.TileChoiceBatch.AddRange(_state.PendingTileBatches[0]);
            _state.PendingTileBatches.RemoveAt(0);
        }
        else if (_state.TileDeck.Count > 0)
        {
            // fallback：機械抽 3 張
            int take = Math.Min(3, _state.TileDeck.Count);
            for (int i = 0; i < take; i++)
            {
                _state.TileChoiceBatch.Add(_state.TileDeck[0]);
                _state.TileDeck.RemoveAt(0);
            }
        }
        if (_state.TileChoiceBatch.Count == 0) return false;
    }
    ...
}
```

兩條路徑共存，舊模組不必改。

## D 部分：多尺寸 tile（1×2 / 2×1 / 2×2 / 3×1 等）

### D.1 動機

當前所有 tile 都是 **1×1**，視覺與敘事彈性受限：
- 「儀式廳」這種重要場所應該比一般房間大（2×2？）
- 走廊、長廊這類線性空間用 1×2 / 1×3 更合理
- 大型戶外（如森林）可以 2×2 表現遼闊

但對技術架構衝擊大，需謹慎評估。

### D.2 三方案對比

| 方案 | 描述 | 優點 | 缺點 |
|---|---|---|---|
| **A** ★ | **「主格 + 尺寸 (W, H)」**：tile 加 `Width: int, Height: int`，主格存資料、佔用格反查主格 | 直觀、資料結構整齊、可表達矩形 | 限矩形（不支援 L 型）|
| **B** | **多 entry 共享 TileId**：每佔用格在 TileMap 都有 entry，TileId 相同，加 `IsMainCell: bool` 欄位 | 結構鬆散 | 每個操作都要找主格，邏輯繁瑣 |
| **C** | **TileFootprint (List of relative offsets)**：tile 定義 `footprint: [(0,0), (1,0), (0,1), (1,1)]` 等 | 最強大（L 型 / T 型 / 不規則）| 最複雜（碰撞判定 / 渲染 / 旋轉等都要重寫） |

**推薦 A**：直接、足夠表達常見大型場景、不過度設計。

#### IsLegalPlacement 多格判定

```csharp
public bool IsLegalPlacement(int row, int col, int width, int height)
{
    // 1. 整個 W×H 區域在邊界內 + 全部未佔用
    for (int dy = 0; dy < height; dy++)
        for (int dx = 0; dx < width; dx++)
        {
            int r = row + dy, c = col + dx;
            if (!IsInBounds(r, c)) return false;
            if (_state.TileMap.ContainsKey((c, r))) return false;
            if (_state.TileOccupancy.ContainsKey((c, r))) return false;
        }

    // 2. 該區域至少有一個外圍格與已放置 tile 4 方向相鄰
    if (!HasPlacedNeighborForArea(row, col, width, height)) return false;

    // 3. Tag 配對（A 部分規則，rectangle 外圍所有相鄰 tile 取交集）
    return AnyAreaNeighborTagCompatible(row, col, width, height, candidateTags);
}
```

### D.4 UI 改動（最大不確定性）

#### TileVisual 多格渲染

當前 1×1 tile 用單一 Polygon2D quad 渲染。Multi-size 兩種策略：

**策略 1：N×M 個小 quad 共享 visualProfile**
- 渲染 N×M 個獨立 TileVisual quad（每個 1×1 大小）
- 每個 quad 看起來相同（同 visualProfile）
- 邊框只在最外圍畫（內部分隔線隱藏）
- **優點**：透視變形自然（每格獨立 ProjectQuad）
- **缺點**：邊框合併邏輯複雜

**策略 2：單一大 Polygon 跨多格**
- 用 1 個 Polygon2D，4 角是「跨 N×M 範圍的外角」
- 透視變形需自行計算（後排小、前排大的整體形變）
- **優點**：視覺上完全是「一個大 tile」
- **缺點**：透視計算複雜，UV 映射要 stretch（紋理拉長可能變形）

推薦 **策略 1**（小 quad 群組），技術風險低。

#### Hover / Click 多格 tile

- Hover 任一佔用格 → 反查主格 → 視覺上整個 tile 統一 highlight（4 個格同時亮）
- Click 任一佔用格 → 都當作 click 該 tile（主格事件觸發）
- 路徑規劃：通過任一佔用格 = 通過該 tile（玩家視為站在 tile 上）

#### MapExpand 放置高亮

- 玩家持有 1×2 tile → 主地圖顯示 N 個合法「主格」位置（每個位置會涵蓋 1×2 範圍）
- 高亮**整個 1×2 範圍**（不只主格），玩家能預覽 tile 會佔哪些格
- Hover 不合法的主格 → 不亮，或顯示紅色警示（如越界 / 與已放置 tile 重疊）

### D.5 交互邏輯

#### 玩家移動

當前移動規則：玩家在格 (X, Y)，可移到相鄰已放置格。

Multi-size 時：
- 玩家「站在」某 tile = 站在該 tile 主格（規則簡化）
- 移動目標：相鄰**佔用格**（含主格與其他佔用格）→ 反查到該 tile 主格 → 玩家位置設為主格
- BFS 路徑：把多格 tile 視為「**節點集合**」，連通條件 = 任一佔用格四方向相鄰

實際上更直觀：玩家位置 = (X, Y) 不變，只是「站在哪個 tile」由 TileOccupancy 反查決定。tile 內移動是 free（不算移動），但很少需要區分。

#### Tile 變化（transformTile）

當 1×1 tile transform 為 2×2 tile：
- **拒絕**（規格保留 size 不可變）
- 或：擴張，但需要 1×1 周圍 3 格是空格（否則 transform 失敗）
- 推薦：**規格規定 transformTile 不可改 size**（候選 tile 與原 tile 必須同尺寸）

#### Tag 配對與多格

候選 1×2 tile 與場上 tile 的 tag 配對：
- 候選的「外圍格」= W×H 矩形的相鄰格（不含內部）
- 至少一個外圍格與已放置 tile 4 方向相鄰且 tag 相容
- 這樣多格 tile 「插入」連通鏈時相對容易（外圍多 = 機會多）

## D' 部分：地塊組（連續放置）— 多尺寸的 1×1 替代方案

### D'.1 動機

D 部分多尺寸 tile 規模 ~10-12 h（TileVisual 多格透視渲染最複雜）。是否有「保留 1×1 grid 簡單性，又能表現大型場景」的中間方案？

**答案是「地塊組」**：
- 1 張概念上的「組合卡」 = N 個 1×1 tile
- 放置時玩家**強制連續放完 N 格** 才算完成這張卡
- 形狀彈性（玩家可放矩形 / L 型 / T 型 / 一字 / 任意連通形狀）

### D'.2 三方案對比（地塊組合 / 多尺寸 / 自由拼接）

| 方案 | grid | 玩家放置方式 | 渲染複雜度 | 規模 | 強制完整？ |
|---|---|---|---|---|---|
| **D 多尺寸** | 1×1 + size W×H | 點 1 次放 W×H | 高（多格透視）| ~10-12 h | ✓（一次放完）|
| **D' 地塊組（連續放）** ★ | 1×1 | 點 N 次（強制相鄰）| 零 | **~5 h** | ✓（連續放完）|
| **D'' 多 1×1 自由拼接** | 1×1 | 點 N 次（自由位置） | 零 | ~0 h（既有 copies）| ✗（玩家可拼一半）|

★ 推薦 D' 為 v1.12 主推 — 兼具「強制完整」與「1×1 簡單性」。

### D'.4 強制連續性規則

**第 1 格**：
- 既有規則（4 方向相鄰已放置 tile + tag 配對）

**第 2 格起**：
- 必須與**已放的同組格之一**相鄰（4 方向）
- tag 配對自動滿足（同 tile = 同 tags，組內格永遠相容）
- **不必檢查與場上其他 tile 的相容**（已透過第 1 格進場）

**形狀彈性**：玩家可放任意連通形狀（矩形 / L 型 / T 型 / 一字）。

```csharp
private bool IsAdjacentToPendingGroup(int row, int col)

    }
    return false;
}
```

### D'.11 形狀規則 — C 混合方案（採用）

**用戶確認 C 混合方案**：自由連通預設 + `groupShape` 可選強制特定形狀。

#### Schema

`tile.json`：
```json
{
  "id": "ritual-hall",
  "groupCount": 4,
  "groupShape": "rectangle:2x2",   // 可選；未指定則自由連通
  ...
}
```

支援的 `groupShape` 字串：
- `"rectangle:WxH"`（如 `2x2` / `1x3` / `3x1`）→ 強制矩形
- `"line:N"`（1×N 一字，玩家放第 2 格選方向）
- 未指定（null）→ 自由連通（玩家放任意連通形狀）

#### 強制矩形實作邏輯

玩家放第 1 格 = 主格（左上角）；後續格自動由 shape 決定位置：

```csharp
public bool IsLegalPlacement(int row, int col)
{
    if (state.PendingGroupCells.Count == 0) {
        // 第 1 格 = 主格，普通規則
        return basicCheck && tagCheck;
    }

    var tile = _module.Tiles[state.PendingGroupTileId];
    if (tile.GroupShape is null) {
        // 自由連通（D' 預設）：相鄰已放同組格
        return IsAdjacentToPendingGroup(row, col);
    }

    // 強制矩形：next cell 必須是 shape 內下一個位置
    var (mainX, mainY) = state.PendingGroupCells[0];
    var nextSlot = ComputeNextShapeSlot(tile.GroupShape, mainX, mainY, state.PendingGroupCells);
    return (col, row) == nextSlot;
}
```

對 `rectangle:2x2`：
- 第 1 格 (X, Y) → 主格
- 第 2 格 (X+1, Y) → 右
- 第 3 格 (X, Y+1) → 下
- 第 4 格 (X+1, Y+1) → 右下

或更彈性：玩家放第 2 格選「展開朝向」（右下 / 右上 / 左下 / 左上），第 3、4 格自動補。

### D'.13 移動 tag 配對 — 強制經過橋接 tile

#### 動機

放置規則（A 部分）已保證相鄰 tile 必至少共享 1 個 tag → 玩家從 underground 直接走到 outdoor 理論上不可能（必經橋接）。但兩個風險：

1. **`transformTile` 改變 tag**：原相容的兩相鄰 tile，transform 後 tag 不再共享 → 出現「斷層」
2. **作者放錯**：模組未寫 tags 時自動降級為「任意相容」，玩家可能找到捷徑

加移動 tag 配對檢查 = 雙重保險，確保 transformTile 後仍維持邏輯連通。

#### 實作

`WorldMap.IsLegalMoveTarget` 加檢查：

```csharp
public bool IsLegalMoveTarget(int row, int col)
{
    if (!IsInBounds(row, col)) return false;
    if (!GetTile(row, col).IsPlaced) return false;
    var (pr, pc) = PlayerPos;
    if (Math.Abs(row - pr) + Math.Abs(col - pc) != 1) return false;

    // v1.12：移動 tag 配對 — 相鄰兩格必須至少共享 1 個 tag
    if (_state is not null && _module is not null)
    {
        var srcTags = GetTileTags(pr, pc);
        var dstTags = GetTileTags(row, col);
        if (!TagsCompatible(srcTags, dstTags)) return false;
    }
    return true;
}
```

`MapPathFinding.FindPath` BFS expand 也加同樣檢查（避免路徑規劃顯示「跨 tag 路線」）：

```csharp
foreach (var (dx, dy) in Directions)
{

    // v1.12：移動 tag 配對檢查
```

#### 效果

- 玩家從 mansion-front-yard (outdoor) 想到 ritual-hall (underground)：
  - 必須走 outdoor → mansion-foyer (outdoor+indoor) → indoor tile → hidden-chamber (indoor+underground) → underground tile → ritual-hall

- 玩家在 underground 區，旁邊若 transformTile 後變 outdoor → 連通斷裂，玩家走不過去（直到場上開新橋接）

```csharp
public bool BeginMapExpand()
{
    if (Mode != InteractionMode.Idle) return false;
    if (_state is null)
    {
        // standalone：保留既有 1 張行為
        if (_tileDeck.Count == 0) return false;
        _heldTile = _tileDeck.Dequeue();
    }
    else
    {
        if (_state.TileChoiceBatch.Count == 0)
        {
            // 1. 優先用模組定義的下一組
            if (_state.PendingTileBatches.Count > 0)
            {
                _state.TileChoiceBatch.AddRange(_state.PendingTileBatches[0]);
                _state.PendingTileBatches.RemoveAt(0);
            }
            // 2. fallback：機械抽 3 張（無 batches 定義的舊模組）
            else if (_state.TileDeck.Count > 0)
            {
                int take = Math.Min(3, _state.TileDeck.Count);
                for (int i = 0; i < take; i++)
                {
                    _state.TileChoiceBatch.Add(_state.TileDeck[0]);
                    _state.TileDeck.RemoveAt(0);
                }
            }
            if (_state.TileChoiceBatch.Count == 0) return false;
        }
    }
    Mode = InteractionMode.MapExpand;
    ModeChanged?.Invoke();
    return true;
}
```

```csharp
public bool SelectFromBatch(int batchIdx)
{
    if (Mode != InteractionMode.MapExpand) return false;
    if (_state is null) return false;
    if (batchIdx < 0 || batchIdx >= _state.TileChoiceBatch.Count) return false;

    var selected = _state.TileChoiceBatch[batchIdx];
    _state.TileChoiceBatch.RemoveAt(batchIdx);
    if (_state.CurrentPlayer.HeldTileId is not null)
    {
        _state.TileChoiceBatch.Insert(batchIdx, _state.CurrentPlayer.HeldTileId);
    }
    _state.CurrentPlayer.HeldTileId = selected;
    ModeChanged?.Invoke();
    return true;
}

public void CancelMapExpand()
{

    if (_state is null) { /* standalone 既有 */ }
    else

        if (_state.CurrentPlayer.HeldTileId is not null)
        {
            _state.TileChoiceBatch.Add(_state.CurrentPlayer.HeldTileId);
            _state.CurrentPlayer.HeldTileId = null;
        }
    }
    Mode = InteractionMode.Idle;
    ModeChanged?.Invoke();
}
```

```csharp
public bool IsLegalPlacement(int row, int col)
{
    if (!IsInBounds(row, col)) return false;
    if (GetTile(row, col).IsPlaced) return false;
    if (!HasPlacedNeighbor(row, col)) return false;

    if (_state is null || _module is null) return true;  // standalone
    var candidateId = _state.CurrentPlayer.HeldTileId;
    if (candidateId is null) return false;

    var candidate = _module.Tiles.GetValueOrDefault(candidateId);
    var candidateTags = candidate?.Tags ?? Array.Empty<string>();
    return AnyNeighborTagCompatible(row, col, candidateTags);
}

public static bool TagsCompatible(IReadOnlyList<string> candidateTags, IReadOnlyList<string> neighborTags)
{
    if (candidateTags.Count == 0) return true;  // 中立橋接
    if (neighborTags.Count == 0) return true;   // 通配符
    foreach (var t in candidateTags)
        if (neighborTags.Contains(t, StringComparer.Ordinal)) return true;
    return false;
}
```

```
     - 否則不相容（UI 不亮起 + API 拒絕）

地塊尺寸：
  - 當前所有 tile 預設 width=1, height=1
  - schema 預埋 Tile.Width / Height（int, 預設 1）
  - 多尺寸 tile（1×2 / 2×1 / 2×2 等）正式支援預定 v2.0
```

### I.2 §3.1.4 MapExpand 階段 — 改批次選擇流程

```
MapExpand 階段流程（v1.12）：
  1. 玩家點 TopBar「抽地塊」鈕 → BeginMapExpand
  2. WorldMap 檢查 TileChoiceBatch：
     - 為空且 PendingTileBatches 非空 → 取下一組（模組定義）填入
     - 為空且 PendingTileBatches 空 → fallback 抽 deck 頂 3 張
     - 非空 → 直接進入選擇階段
  3. RightPanel 三 slot 顯示批次（最多 3 張，含 tile 卡名）
  4. 玩家點某 slot → SelectFromBatch → HeldTileId = 該 tile
  5. 主地圖 4 鄰格依新規則（4 方向相鄰 + tag 配對）高亮
  6. 玩家點目標格 → TryPlaceHeldTile → batch.RemoveAt(已在 SelectFromBatch 時)
  7. （可選）Cancel：HeldTileId 退回 batch 末尾
  8. （可選）Re-select：prev held 退回原 idx，新選定 tile 變持有
  9. 批次清空 → 下次 BeginMapExpand 重新抽下一組（從 PendingTileBatches 或 deck）
```

## K 部分：玩家體驗影響

### 正面（v1.12）
- **策略提升**：玩家從被動「抽到什麼放什麼」變主動「3 張選最佳」
- **空間敘事**：tag 配對引導玩家沿 village → outdoor → indoor → underground 自然探索
- **橋接 tile 變關鍵**：mansion-foyer / hidden-chamber 在 batch 出現時策略性高
- **作者敘事控制**：prologue.tileBatches 讓模組設計者控制節奏（哪幾張 tile 一起出現）
- **減少阻塞**：3 張同時可選，避免「抽到無法放的 tile 被卡住」

### 風險與緩解（v1.12）
| 風險 | 緩解 |
|---|---|
| 批次內 3 張**全部**與場上不相容 | tileBatches 設計上避免（橋接 tile 在合適時機出現）|
| 玩家不知 tag 規則 → 困惑為何某格不能放 | UI hover 不合法格時顯示 tooltip「需含 outdoor 或 village tag」|
| Re-select 行為玩家可能不熟悉 | L2 文件清楚標註「再點別 slot = 換選」|
| Batch 有 1-2 張時玩家少選擇 | 刻意設計（鼓勵橋接 tile 早放）|

### 地塊組連續放置（v1.12 加入）
**正面**：
- 大型場景以「組合卡」表現（儀式廳 4 格組成）
- 1×1 grid 不變 → 渲染 / 移動 / 戰鬥邏輯零影響
- 形狀彈性：自由連通（矩形 / L 型 / T 型 / 一字）+ 可選強制 shape（矩形 / 一字）
- 強制連續 → 不會「拼一半」

**風險**：
- 玩家可能不熟「組」概念 → RightPanel 顯示「N/M」進度引導
- 第 N 格可能無合法位置（被卡）→ 第 1 格放下時預檢周圍空間
- 中途取消玩家流失進度 → 取消邏輯回退所有已放格

### 區塊外框 + 移動 tag 配對（v1.12 加入）
**正面**：
- **區塊外框**：玩家視覺明確分辨「同一張卡的格」（金色粗邊框包住）
- **移動 tag 配對**：強制經過橋接 tile，從地下不能直跑野外
- 兩者共同保證「設計意圖被尊重」：作者透過 tag + groupCount 控制玩家路線

**風險**：
- 外框美術風格需配合（金邊在 paper 主題地圖上要醒目又不喧賓奪主）
- 移動 tag 限制可能讓玩家「卡住」（場上沒橋接 tile 時無法跨區）→ 但這是設計意圖，玩家應主動建橋接

### 縫隙裝飾層（任務 15 美術階段加入）
**正面**：
- 地圖視覺從「散落 tile」變「連續地形」
- 純美術改動，不影響任何遊戲邏輯
- 紋理可從相鄰 tile visualProfile 自動推導，模組作者零負擔

**風險**：
- 透視變形下 gap 形狀不規則 → Polygon2D 跨多邊形 + UV 拉伸
- 美術成本（4-6 種 terrain edge 紋理）→ 與任務 15 一起做

### 多尺寸 tile（Phase 4）
**正面**：
- 大型場景（儀式廳 2×2、長廊 1×3）視覺更宏偉
- 模組作者更彈性

**風險**：
- TileVisual 多格透視渲染複雜度高
- 9×9 空間有限 → 過度使用會限制玩家探索
- transformTile 與 size 改變的規則衝突 → 規定 transform 必須同尺寸
