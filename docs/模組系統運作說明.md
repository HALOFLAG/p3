# 模組系統運作說明

> 寫於 2026-04-27（commit `7be6bf0` 後）。
> 對應規格書 §1.4 卡牌系統 + §5.1 模組系統 + §13-1 開場序幕。
> 讀者：未來模組製作者 / 引擎開發者。

---

## 1. 核心觀念

**模組 = 一個獨立可替換的劇本套件**，由純 JSON 構成，**不需碰 C# / Godot**。
引擎讀取模組後，依模組定義的內容動態生成遊戲體驗。

```
同一個引擎 → 載入不同模組 → 玩出不同遊戲
```

這是規格書 §5.1 的設計目標：**引擎與內容分離**。

---

## 2. 模組完整結構（三層）

```
Module（模組 = 一個劇本套件）
│
├── Manifest（模組身份證 / 外部元資料）
│   └─ 給選單顯示用，runtime 載入時不影響玩法
│
├── Prologue（序幕卡 / 內部遊戲設定 + 開場）
│   └─ Singleton（每模組 1 張）— 承載所有遊戲級設定
│
└── 8 種卡片字典（劇本內容）
    ├── Characters / NpcCompanions
    ├── Tiles / Events
    ├── ActionCards / Equipment
    ├── Battles / Endings
    └─ 每種都是 Dictionary<id, Card>，數量任意
```

實際 `Module` record（[core/Models/Module.cs](../core/Models/Module.cs)）：

```csharp
public sealed record Module(
    Manifest Manifest,                          // 1 個
    Prologue Prologue,                          // 1 個（序幕卡）
    IReadOnlyDictionary<string, Character>     Characters,
    IReadOnlyDictionary<string, NpcCompanion>  NpcCompanions,
    IReadOnlyDictionary<string, Tile>          Tiles,
    IReadOnlyDictionary<string, EventCard>     Events,
    IReadOnlyDictionary<string, ActionCard>    ActionCards,
    IReadOnlyDictionary<string, Equipment>     Equipment,
    IReadOnlyDictionary<string, Ending>        Endings,
    IReadOnlyDictionary<string, BattleCard>    Battles
);
```

序幕卡跟其他卡同等地位，只是**唯一**且**包含遊戲級設定**。

## 3. Manifest 與 Prologue 的職責切分

兩者都是 singleton，但用途不同：

| 維度 | Manifest | Prologue（序幕卡） |
|---|---|---|
| 角色 | 模組「外部識別」 | 模組「內部規則 + 開場」 |
| 何時讀 | 選單列出可選模組時 | 開新局後立即解析 |
| 給誰看 | 玩家**選模組前** | 玩家**選模組後**（含開場 overlay） |
| 內容 | id / 名稱 / 版本 / 作者 / 難度標籤 / 簡述 / 預估時長 | 開場敘事 / 勝負條件 / 難度曲線 / 起始角色同伴 / 結局評分公式 |

### 3.1 Manifest 完整欄位

```json
{
  "id": "abandoned-mansion",
  "name": "廢棄洋房調查",
  "version": "1.0.0",
  "author": "CardNarrative 官方",
  "schemaVersion": 1,
  "description": "一封匿名信...揭開這棟宅邸與它失蹤家族的真相...",
  "estimatedPlayTime": "90-120 分鐘",
  "difficulty": {
    "stars": 3,
    "label": "中上"
  }
}
```

| 欄位 | 必填 | 用途 |
|---|---|---|
| `id` | ✅ | 全域唯一識別字（檔名 / 路徑慣用） |
| `name` | ✅ | 顯示名稱（中文 / 多語） |
| `version` | ✅ | 版本字串（semver） |
| `schemaVersion` | ✅ | schema 版本（1 = 當前） |
| `author` | ❌ | 作者署名 |
| `description` | ❌ | 選單卡片簡介 |
| `estimatedPlayTime` | ❌ | "90-120 分鐘" 等顯示字串 |
| `difficulty.stars` | ❌ | 1-5 星 |
| `difficulty.label` | ❌ | 中文標籤（簡單 / 中等 / 中上 / 困難 / 噩夢） |

### 3.2 Prologue 完整欄位

實際 `Prologue` record（[core/Models/Prologue.cs](../core/Models/Prologue.cs)）：

| 欄位 | 型別 | 用途 | abandoned-mansion 範例 |
|---|---|---|---|
| `ModuleName` | string | 顯示用模組名 | "廢棄洋房調查" |
| `Difficulty` | int | 難度數值（1-5）| 3 |
| `OpeningNarrative` | string | 開場敘事（S1 overlay） | "一封沒有署名的信..." |
| `WinConditions` | List | 勝利條件（flag-based） | 3 個 flag 全 true |
| `WinConditionLabels` | Dict?（init） | flag → 中文標籤對映 | mansion_truth_revealed → "揭開真相" |
| `LoseConditions` | List | 失敗條件（turnLimit / allPlayersDown） | 30 回合 / 全員倒下 |
| `LoseConditionLabels` | Dict?（init） | 失敗條件 → 中文標籤 | turnLimit → "30 回合內未達成" |
| `DifficultyCurve` | DifficultyCurve | TN 隨回合變化 | early(8-10) / middle(10-12) / climax(14, +1/失敗, cap 18) |
| `StartingTileId` | string | 起始格 ID | "village-square" |
| `ImportantTileIds` | List<string> | 重要格清單（影響評分） | 3 個（書房 / 地下室 / 儀式廳） |
| `StartingCompanionIds` | List<string>（Stage 1 加） | 起始 2 同伴 | ["old-priest", "hired-bodyguard"] |
| `CharacterUpgradeThreshold` | int | 角色升級門檻 | 3 |
| `ScoreFormula` | string | 結局評分公式 | "contributions × 2 + equipmentSlotsFilled" |

### 3.3 為什麼把序幕當「卡」而不是「設定檔」？

規格書 §1.4 把 prologue 歸進**卡牌系統**，因為它：

1. **有 narrative**（像事件卡有開場敘事）— `OpeningNarrative`
2. **被「翻開」一次**（像事件卡被觸發）— 開新局時顯示 overlay 一次
3. **有結算邏輯**（像戰鬥卡有 outcome）— WinConditions / LoseConditions / ScoreFormula
4. **有條件評估**（像事件卡有 condition）— flag-based winConditions
5. **schema 驗證**與其他卡同層級

但它跟一般卡不同之處：
- **獨一無二**（每模組僅 1 張）
- **沒有 id**（不需要被其他卡參照）
- **不進牌堆 / 不在 ORBIT**（它「是」遊戲，不是遊戲中的內容）

可以這樣理解：**序幕卡 = 模組的「總綱」卡**，定義了「這個劇本玩什麼、贏什麼、輸什麼」。

## 4. 完整模組三層內容對照

```
[第 1 層：模組身份]
Manifest（manifest.json）
└─ 給玩家選模組看 → "廢棄洋房調查 ★★★ 90-120 分鐘"

[第 2 層：遊戲設定 + 開場敘事]
Prologue（prologue.json，序幕卡）
└─ 載入後決定：
    - 玩家看到什麼開場故事
    - 怎樣算贏 / 怎樣算輸
    - 起始角色 / 起始同伴 / 起始地塊
    - 難度怎麼隨回合升降
    - 結局評等怎麼算

[第 3 層：劇本內容（8 類卡片）]
Characters / NpcCompanions / Tiles / Events / ActionCards / Equipment / Battles / Endings
└─ 載入後成為「資源池」：
    - tiles 進 TileDeck，玩家抽卡 expand
    - events 進 ORBIT，依 trigger 升 ClassA
    - action cards 進 character.StartingDeck
    - equipment 在玩家初始背包 / event outcome grant 給予
    - battles 在 event.triggerBattle 召出
    - endings 達 threshold 後顯示

[嵌入第 3 層內：流程規則]
- tile.transformations           ← Stage 5 加的 tile-side rule
- tile.onEnter                   ← 踩進該格觸發的 effect
- event.outcomes.{Success/Partial/Failure}.effects  ← 結算後套效果
- *.condition (JsonLogic)        ← 條件式 reveal / trigger / transform
- *.tags                         ← 標籤觸發（戰鬥輔助 / 放置規則 plan B）
```

## 6. 模組 ↔ 系統介面（哪些可調 / 哪些固定）

### 6.1 ✅ 模組可完全控制

- 各種卡片資料（含數值、敘事、結構）
- 勝負條件（flag-based 任意組合）
- 起始陣容（角色 / 同伴 / 地塊 / 行動卡 deck）
- 難度曲線（early / middle / climax 三階段 TN）
- 地塊網絡（透過 tags + copies 控制地圖結構）
- 事件樹（透過 trigger + condition + outcome.effects 串連）
- 地塊變化（transformations + JsonLogic 條件）
- 結局評分公式（formula 字串）

### 6.2 🔒 系統內建，模組可挑但不可擴

#### Effect 型別（10 種）

`setFlag` / `grantEquipment` / `grantResource` / `tileProgress` / `triggerBattle` / `climaxTnIncrease` / `rollCheck` / `drawEncounter` / `transformTile` / `transformTilesByTag`

#### Trigger 型別（4 種）

`tileEnter` / `flag` / `turnTimer` / `actionCount`

#### Card 類別（8 種，外加 Manifest + Prologue）

模組無法定義新「卡牌類別」（如「劇情卡」「天氣卡」等），只能用既有 8 種。

#### Terrain 列舉

- 遊戲語意：`Town / Wilderness / Dungeon / Special`（4 種）
- 視覺類別：`Forest / Path / Grass / Water / Mountain / Building`（6 種，逐 tile 透過 visualProfile 指定）

#### ActionType（4）+ EquipmentSlot（8）+ Stat（4）

全 enum，hardcoded。

#### JsonLogic 變數命名空間（規格 §7.3）

固定 8 類：`flag.* / hero.* / companion[i].* / turn / currentTile.* / tile.<row>.<col>.* / orbit.{A,B,C}.count / worldFlags.*`

### 6.3 🚫 完全 hardcoded（不在 schema 中，模組無法影響）

| 點 | 影響 |
|---|---|
| modulePath 寫死在 MainBootstrap | runtime 只認固定路徑（待補完模組可替換性） |
| art/ PNG 路徑寫死 | 模組無法自帶美術（待補完） |
| Schema 路徑全域共用 | 模組不能擴自訂 schema |
| UI 區塊（17 個）由 Godot 寫死 | 模組無法自訂 UI |

## 7. 給模組製作者的指南

### 如何寫一個新模組

假設要做「鬧鬼孤兒院」：

1. **複製範本**：`cp -r modules/builtin/abandoned-mansion modules/builtin/haunted-orphanage`
2. **改 Manifest**：`id = "haunted-orphanage"` / `name = "鬧鬼孤兒院"` / 難度 / 預估時長
3. **改 Prologue（最關鍵）**：
   - `OpeningNarrative` 寫新開場故事
   - `WinConditions` 換新 flag（例：`children_rescued` / `truth_revealed` / `escape_at_dawn`）
   - `StartingTileId` 換新起始格 id
   - `StartingCompanionIds` 換選定的同伴
   - `DifficultyCurve` 視難度調 TN
   - `ScoreFormula` 設定結局評分（可保留或改）
4. **改 Tiles**：重新繪製地圖網絡（孤兒院房間 / 走廊 / 庭院 / 地窖）
5. **改 Events**：寫新事件（孤兒院的鬼故事）
6. **改 Endings**：寫 4 個結局
7. **改 Battles**：設計新戰鬥（小鬼魂 / 院長亡靈 / ...）
8. **改 Characters / Companions**：可沿用 abandoned-mansion 的角色，也可自寫
9. **改 ActionCards / Equipment**：同上

→ **不需碰 C#**，全部都是 JSON。所有規則都用 effect 列舉 + JsonLogic 條件式表達。

### 流程規則寫法範例

#### Tile 加 onEnter effect（踩進該格觸發）

```json
{
  "id": "haunted-classroom",
  "onEnter": [
    { "type": "rollCheck", "stat": "intellect", "tn": 11,
      "onFailure": [{ "type": "grantResource", "key": "fear", "amount": 1 }] }
  ]
}
```

#### Event 多分支 outcome

```json
{
  "id": "ghost-encounter",
  "outcomes": {
    "success": {
      "narrative": "你冷靜地對話，鬼魂緩緩消散。",
      "effects": [
        { "type": "setFlag", "key": "ghost_befriended", "value": true },
        { "type": "grantResource", "key": "clue", "amount": 2 }
      ]
    },
    "partialSuccess": {
      "narrative": "你勉強驅離鬼魂但驚魂未定。",
      "effects": [
        { "type": "grantResource", "key": "clue", "amount": 1 }
      ]
    },
    "failure": {
      "narrative": "鬼魂衝向你！",
      "effects": [
        { "type": "triggerBattle", "battleId": "angry-spirit" }
      ]
    }
  }
}
```

#### Tile-side transformation（Stage 5）

```json
{
  "id": "fragile-floor",
  "transformations": [
    { "triggerEventId": "earthquake", "transformsTo": "collapsed-floor" }
  ]
}
```

意義：當 `earthquake` 事件結算 → 所有 fragile-floor 變 collapsed-floor。

#### JsonLogic 條件（reveal 條件式事件）

```json
{
  "id": "secret-revealed",
  "trigger": { "type": "flag", "key": "found_diary", "value": true },
  "outcomes": { ... }
}
```

意義：玩家找到日記（setFlag found_diary=true）後，secret-revealed 事件升 ClassA。

## 8. 模組可替換性現況 + 補完路徑

### 現況

底層架構**完全 module-agnostic**：
- `Module` 是 immutable record
- `ModuleLoader.Load(folderPath)` 接受任意路徑
- `GameState.CreateNew(module, ...)` 接受任意 module
- 所有 service（TurnLoop / EffectHandler / EventResolver / MapService / EquipmentService）都接 `module` 參數

差「runtime 入口開放替換」這最後一哩路。

### 待補項目

| 項 | 估時 | 重要性 |
|---|---|---|
| 模組目錄掃描（Directory.GetDirectories） | 1 h | 🟢 高 |
| 主選單模組選擇 UI | 3-5 h | 🟢 高 |
| 移除 hardcoded fallback（強制 prologue 完整） | 1 h | 🟢 高 |
| 模組自帶美術（visualProfile.texturePath） | 6-10 h | 🟡 中 |
| 模組打包格式（.zip） | Phase 3+ | 🟢 低 |
| 自訂 effect plugin | 大坑（需 dynamic load） | 🟢 低 |

## 9. 一句話總結

**模組 = Manifest + Prologue（序幕卡 = 遊戲設定）+ 8 類卡片字典**

- **Manifest**：模組外部識別（給玩家選模組）
- **Prologue（序幕卡）**：模組內部設定 + 開場敘事（singleton，遊戲規則總綱）
- **8 類卡片**：劇本內容（characters / companions / tiles / events / actionCards / equipment / battles / endings）
- **流程規則**：嵌在卡片內（transformations / onEnter / outcomes / conditions / tags）

引擎與模組完全分離 → **同一引擎跑無數模組** → 規格書 §5.1 設計目標。
